Transforming and Looking Up IdP Attributes

Overview​

When voters log in through an external Identity Provider (IdP), the IdP often sends values that Step can't store as they are:

  • The value needs a transform. For example, the voter ID arrives as <id>@<domain> and the username must be <id>.
  • The value has to be translated into a Step value. For example, the IdP sends a region and a precinct, and Step needs the voter's area.

The Attribute Transform and Lookup identity provider mapper handles both. It works with SAML and OIDC identity providers and runs these steps on every login:

  1. Source: reads one or more SAML attributes or OIDC claims.
  2. Extract: keeps part of each value, using a regular expression (optional).
  3. Normalize: trims each value and sets its case.
  4. Join: joins the values with a separator when there are several sources.
  5. Validate: checks the joined value against a regular expression (optional).
  6. Lookup: translates the value through a table (optional).
  7. Target: stores the result in a user attribute, or in the username of a new user.

If a step produces no value, the mapper leaves the target unset, stores a default value, or rejects the login, as configured.

Prerequisites​

  • Access to the Keycloak Admin Console.
  • The sequent.idp-attribute-mapper.jar extension in Keycloak's providers/ directory (included in the Sequent Keycloak Docker image).
  • A SAML or OpenID Connect identity provider configured in the election event realm.

Step 1 – Add the Mapper​

  1. In the Keycloak Admin Console, select the election event realm.
  2. Navigate to Identity providers and select the identity provider.
  3. Open the Mappers tab and click Add mapper.
  4. Set Mapper type to Attribute Transform and Lookup.
  5. Fill in the configuration (see below) and click Save.

Add one mapper for each value you need, for example one for the username and one for the area.

Lookup Table Format​

Each line is one of:

  • <value> = <key>, <key>, <from>..<to>: every listed key, and every key in each range, maps to <value>.
  • <key>,<value>: one key per line, for tables generated from another system.

Empty lines and lines that start with # are ignored. Both formats can be mixed.

A range covers the keys that share the prefix of <from> and whose last run of digits lies between the digits of <from> and <to>. <to> can repeat the prefix or give only the digits. When both bounds have the same number of digits, a key must have that many digits too: 09:0001..09:0420 matches 09:0007 but not 09:7. An exact key wins over a range.

# area id = region:precinct keys
4b1f0c1e-3a3e-4f6e-9d1a-0c6c8f1d2a11 = 09:0001..0420, 09:0500
7c2e9b44-8d0f-4b9a-a1e3-5f2d6b7c8e22 = 09:0421..0499, 09:0501..0900

The table is checked when it is first used. Duplicate keys with different values, overlapping ranges, reversed ranges and lines in neither format make the configuration invalid. A login through an identity provider with an invalid mapper fails with a generic error, and the Keycloak log says which line is wrong.

The table is parsed once and kept in memory until the mapper configuration changes. A login only does an in-memory lookup and makes no network calls.

The mapper checks the values on every login, whatever the sync mode, so REJECT also applies to returning voters.

Example – OIDC​

The same mappers work with an OpenID Connect identity provider. Use claim names as Sources, for example region and precinct, or a dotted path such as address.region. The mapper looks for each claim in the access token, then the ID token, then the user info response. Request the scopes that release those claims in the identity provider's Scopes setting.

Loading a Large Table through the Admin REST API​

A table for a large election can have tens of thousands of lines, which is impractical to paste into the Admin Console. Load it with the Admin REST API instead.

  1. Get an admin access token:

    TOKEN=$(curl -s -d grant_type=password -d client_id=admin-cli \
      -d username="$ADMIN_USER" -d password="$ADMIN_PASSWORD" \
      "$KEYCLOAK_URL/realms/master/protocol/openid-connect/token" | jq -r .access_token)

  2. Find the mapper:

    curl -s -H "Authorization: Bearer $TOKEN" \
      "$KEYCLOAK_URL/admin/realms/$REALM/identity-provider/instances/$IDP_ALIAS/mappers" \
      | jq '.[] | select(.identityProviderMapper == "sequent-attribute-lookup-idp-mapper") | {id, name}'

  3. Replace its table with the contents of areas.txt:

    MAPPER_ID=<id from step 2>
    curl -s -H "Authorization: Bearer $TOKEN" \
      "$KEYCLOAK_URL/admin/realms/$REALM/identity-provider/instances/$IDP_ALIAS/mappers/$MAPPER_ID" \
      | jq --rawfile table areas.txt '.config["lookup.table"] = $table' > mapper.json
    curl -s -X PUT -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
      --data @mapper.json \
      "$KEYCLOAK_URL/admin/realms/$REALM/identity-provider/instances/$IDP_ALIAS/mappers/$MAPPER_ID"

  4. Check the Keycloak log on the next login. It reports the number of table entries and the parse time, or the line that makes the table invalid.

Test the new table with a login before voting opens: an invalid table fails every login through the identity provider.
