Notes​

[a] Injecting the resolution into velvet prepare_tally_for_area_contest calls contest.insert_resolved_tie_resolutions(resolutions) (ballot.rs:1581) before writing contest-config.json. This adds a pre_resolution field under RESOLVED_TIE_RESOLUTIONS_KEY that velvet reads instead of invoking EXTERNAL_PROCEDURE. Only applies when tally_type = ELECTORAL_RESULTS; initialization reports always use RANDOM tie-breaking.

[b] Where velvet records the tie During do-tally, RunoffStatus::run() sets pending_tie_resolution on RunoffStatus when it cannot break a tie deterministically. The entire RunoffStatus (including resolved_tie_resolutions and pending_tie_resolution fields) is serialised into process_results and written to contest_result.json on disk. Windmill reads it back via state.get_results() → GenerateReports::read_reports().

[c] Two submission paths The resolution can be submitted via the Admin Portal UI (calls the Harvest REST endpoint POST /submit-tally-resolution) or via step-cli submit-tally-resolution (uses a GraphQL mutation). Both converge on submit_tally_resolution in tally_resolution.rs. Re-submitting an already-resolved record is allowed (admin can change their decision) as long as at least one of the submitted contest IDs is still pending.
