Certified Imports and Readiness Checks

Configure the intended tenant using step-cli step config as described in the getting-started guide. The account needs voter import permission for imports and readiness-check for readiness checks. Use the manager runbook for the rehearsal, witnesses, custody, schedules and evidence required around these commands.

Import a certified voter file​

For signed configuration packages, configure Required SHA-256 and Seal at close in the source before producing and approving the tested and official packages. Verify the selected source configuration or preset explicitly includes both policies before signing. JSON policy fields participate in the signed ballot-design digest; changing an admitted policy can invalidate publication verification. Obtain corrected higher signed and approved revisions when the source policy needs correction.

The expected hash must come from the independent certified transmittal. Import the identical certified full registry into the tested and official events. Earlier rehearsals may use separately certified test data; the event selected for readiness comparison must match the official registry:

step-cli step import-voters \
  --election-event-id "$OFFICIAL_EVENT_ID" \
  --file-path certified-voters.csv \
  --sha256 "$CERTIFIED_SHA256"

step-cli step import-voters \
  --election-event-id "$TESTED_EVENT_ID" \
  --file-path certified-voters.csv \
  --sha256 "$CERTIFIED_SHA256"

--sha256 supplies the declared 64-character hexadecimal SHA-256. The server compares it to the exact uploaded bytes before writing voters. An event with presentation.file_integrity_policy = "REQUIRED_SHA256" refuses missing hashes. Older events default to "OPTIONAL"; an import without a verified declared hash cannot establish certified readiness evidence. The command waits for task completion and exits nonzero on failure or timeout. Retain the successful VotersImported log entry and independently verify its area counts against the transmittal. Count-map keys are trimmed area.name values matched to manifest.content.ballot_designs[].area. Do not substitute the last delta file for a full certified registry.

A FAILED task is terminal. Fix the reported cause and submit a new import command to create a new task; do not retry the old task. A failure during voter commit or completed-import receipt persistence requires reconciling the current registry, area counts and log evidence against the certified transmittal before submitting the new import. The failed task alone does not prove that no voter changes occurred.

Compare the tested and official events​

After closing and sealing the tested event and publishing the unopened official event, run:

step-cli step readiness-check \
  --official "$OFFICIAL_EVENT_ID" \
  --tested "$TESTED_EVENT_ID" \
  > readiness-after-rehearsal.json

Both events must be distinct and belong to the configured tenant. The server derives the actor from the authenticated account. The command writes the JSON report to stdout, diagnostics to stderr and exits nonzero when a check fails or the signed record cannot be confirmed. Inspect the exit status before accepting the report as a pass.

The report contains passed, checked_at, named checks with their verdicts and explanations, evidence for both events and log_entry_id on success. Each check's message is the condition it checks. A failed check also has findings, one per failed condition, each with a stable code, the event it was observed on (official, tested or both), the affected area or election_id when there is one, the observed values and an English message. For example:

{
  "kind": "certified_voters",
  "passed": false,
  "message": "Both events have the same certified file, full current registry counts per area and signed import evidence",
  "findings": [
    {
      "code": "registry_count_changed",
      "event": "official",
      "area": "Area A",
      "values": {"current": "4", "imported": "3"},
      "message": "The official event's registry has 4 voters in area Area A but the certified import has 3"
    }
  ]
}

Passing checks have no findings, so a signed report keeps its shape, and reports written before findings existed still read. Findings carry area names, election IDs, counts and digests, never voter data. When the check cannot be completed, the error names the step that stopped it without internal detail.

The report compares approved package content and approvers, certified voter hashes and area counts, official zero state, official publication designs and tested close/seal completeness. Each event's evidence includes current_voter_counts, voter_import_in_progress and received_ballot_count. Current voter counts must match the certified import, and no import may remain active. Any ordinary official-event ballot, including a record received at ballot review before casting, blocks the zero check. Until an explicit practice-ballot designation and storage isolation are implemented, use isolated practice events; official-event practice cannot currently be certified. The report is a snapshot at checked_at.

Both events' active publications must together contain every ballot design in their signed manifest. Separate publications per election are supported; their references are listed in publication_ids. An incomplete set cannot establish readiness, even when every published design is approved. The tested event's required seals come from these publications; generated but unpublished drafts and retired styles do not add required boxes.

A successful invocation appends ReadinessVerified to the official event log as a USER event under the authenticated account; a failed check does not. In the existing Logs tab, filter statement kind to ReadinessVerified, open the entry and correlate its report with the returned reference. Export CSV/PDF logs through the existing export action. Keep the complete JSON alongside the exports.

For the ERT/FTL procedure, compare the closed, sealed FTL event with the official event, then archive FTL. When the official event's scheduled lockdown starts, confirm its read-only lockdown status and retain LockdownChanged, then run:

step-cli step readiness-check \
  --official "$OFFICIAL_EVENT_ID" \
  --tested "$TESTED_EVENT_ID" \
  > readiness-at-lockdown.json

Here $TESTED_EVENT_ID must still identify FTL. Inspect the command exit status and retain the second ReadinessVerified reference alongside the first report and both events' exported logs in the FTL evidence folder. The readiness verdict does not require lockdown; verify the reported official locked_down value is true for this second execution. ERT has its own evidence folder, including its tally; FTL has no tally.

An intentional new invocation is a new snapshot. Neither invocation opens voting, clears ballots, changes seals or replaces the operational approval procedure.
