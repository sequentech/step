Vitrine transparency logs

Vitrine is Sequent's data-transparency toolkit. An election event can publish its ballots and its milestones in Vitrine transparency logs: voters get a receipt that their ballot is in the log, and observers and auditors can check that everyone is shown the same log. This page describes how step's backend uses Vitrine, how a deployment is configured, and how to run Vitrine in the development environment. The integration's design is docs/step-integration.md in Vitrine's repository; the formats are in its specs/ directory.

Step depends on no Vitrine Rust crate. Its backend talks to the vitrine-log sidecar over HTTP and encodes the log entries itself, and its tests check that encoding against Vitrine's test vectors. The portals and the ballot verifier make every check with the vendored @vitrine/verify package, in the browser; the backend makes none for them.

Transparency never blocks voting: no Vitrine failure fails a cast. The one Vitrine check that stops the booth is its check of the election's configuration before it encrypts a ballot.

Overview​

An event's transparency mode, presentation.transparency, is disabled (the default, also when the key is absent), public or private. A transparent event has two logs on the sidecar:

LogProfileEntriesHow they arrive
ballotsvitrine/election/ballots/v1One per accepted ballot and stage: received at review, then cast or audited (a direct cast writes received and cast together)The ballot box writes the entry to the log's queue in the event's electoral-log database, in the transaction that stores the ballot or its step.
eventsvitrine/election/events/v1Each election's configuration, voting-opened, voting-closed, and a milestone when a tally completes and when results are publishedWindmill posts signed statements to the sidecar's POST add, with the log's submission token.

Witnesses co-sign the logs' checkpoints. The event's trust policy names the logs, their keys, the witnesses and the quorum of witnesses that a receipt needs. Step drafts the policy, the Electoral Board seals and signs it, and step installs it in both logs.

In a public event, anyone can read the logs. In a private event, only the policy's auditors can read them, and voters reach their receipts through Harvest. Vitrine's log engine doesn't run private logs yet, so for now only public events work end to end.

Architecture​

Where things are stored​

  • presentation.transparency and presentation.vitrine, in the election event's presentation, hold what voters read: the policy ID, the sealed policy (public events only), and each log's URL and origin. They never hold a token, a secret or a private key.
  • presentation.hub_updates, in the same presentation, holds the two switches of the Transparency tab's Updates from hubs: confirmation and cast_email, each "on" or "off". A switch that is absent is on, so events from before the setting offer hub updates. The admin portal writes them with the permission election-event-write, and the trigger below does not guard them: they only decide what voters are offered, and can change at any time.
  • presentation.authority_contact, in the same presentation, holds the election authority's contact as the admin typed it in the Transparency tab: up to four text values, name, email, phone and url. Windmill drafts the policy's contact lines from it (see the draft policy below). The admin portal writes it with election-event-write, checks each value by the policy's syntax before it saves, and shows the fields read-only once voting has opened. Nothing else reads it: voters see the contact only from the pinned policy.
  • sequent_backend.vitrine_log holds each log as the sidecar created it: its name on the sidecar (<tenant id>/<event id>/<log>), its log ID and instance ID, origin, URL and keys, the events log's submission token, the log's acknowledgement of the policy, its witness enrolment note, and when it was frozen. Hasura doesn't track this table, because of the token: only Harvest and Windmill read it.
  • sequent_backend.vitrine_event holds the uploaded signed policy and its ID, and the salt of a private event's draft.
  • sequent_backend.vitrine_statement holds the statements that Windmill logged in the events log, with their entries, leaf hashes and, once a checkpoint that meets the quorum covers them, their receipt chains.
  • vitrine.queue_<log id>, in the event's electoral-log database, is the ballots log's queue. The sidecar creates it and its vitrine schema; the ballot box only inserts into it.

The trigger guard_election_event_transparency_update refuses Hasura updates of presentation.transparency and presentation.vitrine once voting opened in the event. Harvest and Windmill enforce the same lock themselves.

Making an event transparent​

The election event's Transparency tab uses three Hasura actions, all handled by Harvest and allowed with the permission election-event-transparency-tab:

  1. enable_transparency(election_event_id, mode) sets the mode to public or private while voting hasn't opened. It refuses public while any election has num_allowed_revotes other than 0: a public ballots log shows a coercer whether a voter cast another ballot after the one they watched, so voters must be able to vote again as often as they need. It creates the ballots and events logs with the sidecar's POST /admin/logs, in the event's electoral-log database, and stores them.
  2. get_transparency(election_event_id) returns the mode and why public is refused, whether the mode is locked, the sidecar's view of the logs and their status, the draft policy, the uploaded policy and its ID, the logs' enrolment notes, and the explorer URL of the policy.
  3. The Electoral Board seals the draft with Vitrine's CLI (vitrine policy seal), and its authorities sign it as the policy's sign line requires.
  4. upload_transparency_policy(election_event_id, signed_policy) checks that the policy is for this event, its mode and its elections, and installs it in both logs with PUT /admin/logs/<name>/policy. The sidecar refuses a policy that isn't sealed or isn't valid. Harvest stores the policy, its ID and each log's acknowledgement, and fetches each log's witness enrolment note with GET /admin/logs/<name>/enrolment.
  5. The witnesses' operators post the enrolment notes, which the Transparency tab shows, to their witnesses. Until a witness has a log's note, it doesn't co-sign that log. In development, Harvest posts them itself (see HARVEST_VITRINE_DEV_WITNESS_ADMINS below).

Casting a ballot​

  • The entry. Harvest casts through Windmill's insert_cast_vote, which computes the ballot's accepted_at once, in whole seconds, and binds it as a parameter, so that the stored ballot and its election/v1 entry agree. ACCEPT_WITH_VITRINE stores the ballot and inserts the entry into vitrine.queue_<log id> in the same transaction, and returns the entry's leaf hash.

  • Idempotent casting. A retried cast with the same ballot_id from the same voter, in the same election, returns the original acceptance: the same stored ballot, the same entry and the same receipt. The same ballot_id from another voter is still refused.

  • The receipt. Harvest then waits for the entry's receipt on the sidecar's internal listener (GET <log>/wait/<leaf hash>?timeout=600), within a budget of 800 ms. InsertCastVoteOutput.vitrine is null when the event's transparency is disabled; otherwise it has a kind, a text (data for the portal, never shown as is) and, for queued and unavailable, a reason:

    kindtextWhen
    receiptThe receiptThe log sequenced the entry within the budget.
    promiseThe promiseThe log promised to sequence it within the policy's mmd.
    queuedThe entry, in base64The log hadn't sequenced it when the wait ended.
    unavailableThe entry, in base64, if there is oneSomething went wrong: the cast still succeeded.

    The reasons are queued, unknown-entry, rejected, frozen, busy, log-unavailable, timeout, unreachable, breaker-open, bad-response, not-queued and no-log. The portal asks for the receipt later with the entry.

  • The circuit breaker. After 5 failures in a row that show a sick sidecar (busy, log-unavailable, timeout, unreachable and bad-response), Harvest stops calling it for 30 seconds, so that casts lose no time. Then one cast tries again: its success closes the breaker, its failure opens it for another period.

Receiving at review, then casting or auditing​

With the event's Receipts signed by the ballot box setting, a ballot goes through the ballots log in steps, each its own entry with a stage: received, then cast or audited. The profile's rules check that a ballot has one entry per stage, is cast or audited but not both, and that a cast or audited entry follows a received one.

  • Receive (POST /receive-ballot). When the review screen opens, the portal sends the voter-signed ballot. Windmill runs the cast checks, stores it in ballot_box_received and queues its received entry in the same transaction, then answers with the ballot box's signature (step/ballot-received/v1) and the log's receipt, promise, queued entry or reason, as for a cast. The portal turns Cast ballot on once it has checked the signature and, with transparency on, the log's receipt or promise for the received entry it computes itself. A queued entry or a log it cannot reach leaves the signature, and the portal asks the log again. The monitors keep the promise, so a log that breaks it is caught without the voter.
  • Cast (POST /cast-ballot). The same voter key signs the cast of the receipt key the ballot box signed at review (step/ballot-cast/v1); the ballot is not sent again. Windmill stores the cast vote, marks the received ballot cast and queues the cast entry in one write, and signs a cast receipt (step/ballot-cast-receipt/v1). The portal checks the receipt or promise for the cast entry before it opens the confirmation screen. The same signature again is a retry and gets the same receipt.
  • Audit (POST /audit-ballot). Auditing a received ballot queues its audited entry and stops it from ever being cast. Once the ballot box confirms the audit, and the audited entry checks, the portal calls audit_ballot again with auditable_ballot. Windmill checks that it is the audited ballot (hash, voter key, ballot style and ciphertexts) and stores it once; the answer's publication says whether it is published, and the audit screen says plainly when it isn't.
  • A reload drops the key that casts the ballot. The portal keeps a marker (no key and no choices) once the ballot box has the ballot, and after a reload the review screen says Your ballot was not cast and offers Back to my ballot.

Telephone voting has no voter device to check a receipt, so it keeps casting directly through insert_cast_vote, which queues the received and cast entries together.

Statements in the events log​

Windmill beat runs schedule_vitrine_statements every 15 seconds (the beat option --vitrine-statements-interval). It queues log_vitrine_statements for each transparent event with statements to log or receipts to keep. A status change that opens or closes voting in a transparent event queues a run at once. A run logs, in this order:

  1. When the event's first election opens: a vitrine/config/v1 statement for each election, then the voting-opened milestone, with a config line per election that names its config entry's leaf hash. Step can publish an election's ballots again until voting opens, so its key and ballot styles are final then.
  2. When a tally completes and when results are published: a milestone, tally-completed or results-published.
  3. When the event's last election closes: voting-closed, with each election's ballot count.

A config statement names the hashes that the booth compares before it encrypts:

  • key: the base64 SHA-256 of the election public key's bytes, as the booth encrypts to it.
  • styles: the base64 SHA-256 of the concatenation, in ascending byte order and without repeats, of the 32-byte SHA-256 digests of the election's ballot styles, each over the exact text that the voting portal receives. Two areas with byte-identical styles give one digest.
  • release: sequent/voting-portal <version>, from WINDMILL_VITRINE_PORTAL_VERSION. The deployment sets it and the portal's APP_VERSION from one value.

Windmill signs each statement with the operator's authority key and stores it before it submits it, so that every retry submits the same bytes. It then waits for the entry's receipt (GET events/wait/<leaf hash>), upgrades it to a checkpoint that meets the policy's quorum, and stores the receipt chain.

Vitrine has one voting window per event, spanning all its elections, while step can open, pause and close elections separately. So pausing writes nothing, an election's ballots can't be published again after voting-opened, and a transparent event can't reopen after voting-closed.

What voters' booths get​

Two more Hasura actions, for voters:

  • vitrine_voter_context(election_event_id, election_id) returns what the booth must hold before it encrypts: the mode, the policy and the ballots log's acknowledgement of it, the election's config statement and the voting-opened milestone (each with its entry and receipt chain, or null until Windmill logged it), the hex SHA-256 of each of the election's distinct ballot styles, sorted, and the release.
  • vitrine_voter_forward(election_event_id, route, body, hub), for private events only, forwards upgrade, opening and policies requests to the sidecar's internal voter routes. upgrade and opening require a receipt or promise owned by the logged-in voter; opening also names a hub. policies requires an authenticated voter of the event, an empty body and no hub. Harvest supplies the server administrator bearer and voter identity to the sidecar; neither is exposed to the browser.

The private version-1 policy-proofs frame supplies supplemental inclusion only. It cannot establish that no policy entries were omitted, their earliest quorum times, complete discovery freshness or automatic successor adoption. The SDK therefore retains the independently accepted history and leaves those claims pending even for an authentic selective frame. A full private events prefix is never forwarded to voters. Public discovery can check a complete prefix for absence and order; a new candidate still needs a separate earliest-quorum proof before adoption.

What the portals show​

The admin portal's Transparency tab follows Vitrine's design board for the event's overview. It shows only what get_transparency returns, and says "Not reported" for the rest instead of guessing:

  • The record's health comes from the stored policy, the logs' reported alerts and their witnesses: it is healthy unless the stored policy is invalid, a log runs under another policy ID, or a log or witness reports an alert.
  • Figures the sidecar reports: the entries in the logs' witnessed checkpoints, the sequencer queue and how long its oldest entry has waited, and when an app hub last received an anchor. Not reported: the accepted rate, the receipt time, the browser layer, overdue promises, evidence reports, the booth release and which milestones the record holds.
  • Witnesses, hubs, monitors and redactions come from the sealed policy, with each witness in its worst state across the event's logs.
  • Visibility is the mode the logs were created with, locked once voting opened. The draft, upload and enrolment workflow stays below the overview.

The voting portal's flow stays as it is, with additions when the event's transparency is on: a check mark next to the Tracking ID, the name the voter sees for the ballot's ID (ballot_id in the API and the database), and a tag that says Not cast or Cast. The Tracking ID is the first 32 bytes of SHA-512 over step/ballot-id/v2, the ballot's hash and the voter key's DER (empty without a key), each length-prefixed, written in Crockford base32 in hyphenated groups of four, as in FTBE-MHRX-71J7-…. The first two groups are the short ID. Voter pseudonyms use a colon instead (K7QM:2XWD), so the two never read as each other. A lookup ignores case and hyphens, reads I and L as 1 and O as 0, and needs at least 8 characters. A short ID finds ballots and never proves one is the voter's: when it fits up to 5 ballots they are listed, each with its full ID, and above that the page asks for the third group (four more characters). Where the event is public, the browser asks a log server or monitor of the policy for the whole bucket of ballots whose Tracking ID starts with the first 3 characters, with GET <server>/lookup/<log>/tracking-bucket/<3 characters>, and keeps the ones that share the typed groups itself, so no server learns which ballot was looked for. A server that has no such route (404) is skipped, and when none of the policy's servers has it, the lookup that sends the typed ID to the election's server takes over, and the page says that this server sees the exact ID. A voter who then opens one of the listed ballots does send its ID to that server, to get the ballot's content. On the review screen the ID sits in a box next to the title on a wide screen. The check mark shows how far the receipt's check has got: not cast yet on the review screen, then checking, in the public record, confirmed by witnesses, verified, late or problem. The worst step wins, and it is blue only when every tier the policy uses is verified. Selecting it opens a dialog with the short and full ID and three steps: in the public record, confirmed by witnesses and anchored publicly. The dialog also has two states for an audited ballot: the audit screen's Tracking ID box opens it as auditable, tagged Audited, and Step doesn't use audit failed today. Contradicting signed proofs, or a required receipt that never came, show as a problem, and never turn an accepted cast into a failed one. The portal keeps no receipt or Tracking ID in the browser, so the election list says Voted with no check mark, and Click to Vote is off once the voter cast every ballot an open election allows. The ballot tracker, Ballot Tracking, shows the whole receipt, for a ballot found by its short or full Tracking ID, and the ballot's record in a viewer that expands, copies and saves it. Step publishes a ballot the voter audited, and when the record that the tracker finds for a Tracking ID is an audited ballot, the tracker checks it in the voter's browser and shows its selections.

A hub's ballot verifier​

A hub whose policy line hub-ballot-verifier <name> <url> names a ballot verifier runs Step's ballot verifier app there. The voting portal links an audited ballot into it as <url>tenant/<tenant>/event/<event>/election/<election>/audited#id=<full Tracking ID>&policy=sha256:<hex> (Windmill builds the same link with hub_sites::audited_ballot_link). The fragment never reaches the hub's server. The page needs no login or upload. It uses the election's policy only if it is pinned or in the event's public config with the link's ID. It finds the ballot in a bucket of the ballots log, proves its audited entry with the log's receipt, and reads the events log for successor policies. Then it takes the ballot and the secret the portal published from the public ballot locator (locate_ballot with no token, which finds only published audited ballots, at most one lookup every 200 ms per address), and checks that they give the Tracking ID and reproduce the ciphertext. Only then does it decode the ballot in the browser, for the voter to compare with what they chose. It never fetches or decodes a cast ballot. The verifier's global-settings.json can name the hub (HUB_NAME, its name in the policy) for the page's header, and the voting portal (VOTING_PORTAL_URL) for "Back to the voting site".

Updates from the policy's hubs​

A hub that the policy gives a site (hub-explorer <name> <url>) can tell a voter by email when their ballot is confirmed and counted. Step never takes the voter's address: it sends the voter to the hub's site, where they enter it and choose what to watch. Every hub with a site is offered equally, in a random order, with no default and no label that ranks one above another. The link into a hub is <hub-explorer url>#policy=<sha256:hex>&watch=<base64url receipt> when the portal holds the receipt, and <hub-explorer url>#policy=<sha256:hex>&watch-id=<full Tracking ID> when only the Tracking ID is known (the receipt PDF and the cast email). The payload sits in the fragment, which a browser never sends to the hub's server.

  • The confirmation page shows a "Get email updates" callout when hub_updates.confirmation is not off, the event is transparent, the policy has a hub with a site, and the voting portal is not the kiosk. The order is drawn once for each visit. The payload is the receipt chain, once the browser has it; before that the link names only the policy.
  • The ballot receipt (the BALLOT_RECEIPT template) gets two variables. tracking_id is the ballot's full Tracking ID, which the default template prints in place of ballot_id when it is set. hubs is a list of {name, operator, url} in a random order for each receipt, and is empty unless the event is transparent and hub_updates.cast_email is not off. Each url carries the Tracking ID as watch-id. Custom templates keep working without either variable.
  • The cast email. When a BALLOT_RECEIPT report is sent by email (a report task with recipients, or a voter ID, sends it), the email's text gets a section below the template's own: the ballot's full Tracking ID and one link to each hub, in the receipt's random order, one to a line, in plain text. An HTML body gets the same section before </body>. The switch is the receipt's: with no hubs (not transparent, hub_updates.cast_email off, or no hub with a site) the email is the template's text untouched. If the ballot can't be read again when the email goes, it goes without the section and the log says so. Step's own ballot-receipt task passes no recipients and no voter ID (the receipt route keeps the real voter ID out of the task), so it sends no email: a deployment that emails the receipt adds the recipients.

Each hub's name and operator come from the policy, and a hub whose site is not a plain HTTP(S) address without credentials is left out. The admin portal lists the hubs read-only under the switches, in the policy's order, and says that voters see them in a random order.

Deleting, exporting and importing events​

  • Deleting a transparent event freezes its logs first, with POST /admin/logs/<name>/freeze. The deletion fails if a freeze fails, unless the sidecar doesn't know the log.
  • An event's export leaves the vitrine schema of its electoral-log database out. An imported event's transparency is disabled, since the logs belong to the event it was exported from.

The deployment configuration​

Harvest drafts each event's policy from the deployment configuration, a TOML file that HARVEST_VITRINE_CONFIG_FILE names, and from the event. The development environment's is .devcontainer/vitrine/deployment.toml. Harvest checks it whenever it reads it, against the rules of Vitrine's specs/policy.md, section 3, that the configuration decides, so that every draft made from it is valid. Unknown keys are errors.

Names (of authorities, auditors, witnesses, groups, monitors, hubs and parties) are 1 to 64 bytes of A-Z a-z 0-9 . _ -, and not none. URLs are https, or http on localhost, 127.0.0.1 or [::1]. Verifier keys are signed-note vkeys: Ed25519 for authorities, auditors, monitors and hubs, and cosignature/v1 for witnesses.

Harvest also checks that:

  • no key appears twice anywhere in the configuration, and the logs' own keys are none of them;
  • with the operator's witnesses counted as faulty, two inconsistent checkpoints can't both meet a quorum, and the quorum tolerates min_faults more faulty parties;
  • with app hubs, the witnesses have distinct key names, and there are at most 31 of them;
  • a bootstrap hub isn't run by the operator or the platform and is independent of every app hub, and the app hubs meet [anchor_hubs] and the unconditional election-profile floor;
  • the profile bindings equal the two reviewed built-in meaning hashes in the configuration. Unknown, obsolete or future meanings need an explicit integration update and are refused.

What comes from the event​

The draft takes its name (<tenant slug>/<event id>, or <tenant id>/<event id> when the slug can't be a name), visibility (the mode), required on, and for a private event a random policy-salt, from the event. Private drafts also include a blinded line for each log: Harvest calls the authenticated, idempotent POST /admin/logs/<name>/blinded-key with the derived pseudo-origin. The sidecar generates and durably stores the secret keys; Step keeps only their public vkeys. Both modes retain the hubs and monitor requirements. Its opens is the earliest scheduled start of the event's elections and closes the latest scheduled end, grace periods included: the policy can't be drafted while an election has no scheduled start or end, its own or the event's. Its quiet period is the last 3600 seconds before closes, or the whole window if it is shorter. The ballots log's param lines name the event and its elections. Each log's log, log-time, mirror, mirror-party and profile lines come from the logs that the sidecar created and the configuration. Everything else comes from the configuration.

Two lines follow the deployment, not the event. platform is the configuration's platform (Sequent by default) and sits right after operator. anchor-hubs is 2 1 when the configured hubs allow it, so that at least one hub is run by neither the operator nor the platform; a stronger [anchor_hubs] rule is kept, a weaker one is raised to it. A draft has no words line. The contact lines come from the election event's presentation.authority_contact, one line for each kind that is set, right after platform, in the order name, email, phone, url. Each value follows rule 19 of the policy specification: a name is 1 to 128 bytes of text with single spaces and no line breaks, control or format characters; an email is an ASCII local@domain address of at most 254 bytes; a phone is + and 7 to 15 digits, the first not 0; a URL is an absolute https URL, so http is refused even on localhost. Windmill reads the stored contact tolerantly and leaves out a kind that is empty or breaks its syntax, with a warning in its log, so that the draft the Board seals is always valid; draft itself refuses a contact that breaks it. A draft without a contact has no contact lines. A successor policy may change the contact even after voting opens, but the tab locks the fields then. Until the policy carries a contact, voters see the contact in the portal only as "From the election's settings", never as the policy's.

Problems that the hubs list​

A hub lists the problems it has recorded for a policy at GET <hub>/problems?policy=sha256:<hex>, which answers {hub, problems: [{id, kind, subject, policy, logged_at, entry}], more}. Each row points to an evidence file that anyone can check, and the hub's site opens it at <hub-explorer url>#policy=<sha256:hex>&problem=<evidence hex>. The voting portal's Ballot status dialog and the admin Transparency tab ask every hub of the sealed policy once (two pages of 50 rows at most) and show a notice when any of them lists a problem. Each app keeps the call in one small module (services/vitrine/hubProblems.ts in the voting portal, services/HubProblems.ts in the admin portal), because the SDK has no client for it yet. The notice names each kind in plain words ("Two versions of the record" for split-view, "A promised entry is missing" for broken-promise, "An entry breaks the rules" for bad-entry, hub-entry, time-regression and bad-checkpoint, "Two policies" for policy-equivocation and "Code that isn't logged" for unlogged-code), never by its code, and any other kind as "A problem recorded by a hub". It names the hubs that list the problem and links to the proof on the hub's site, and it says that it is a convenience of the portal: it works only while the portal tells the truth, and the hubs' emails, sites and the extension work even if it does not. A hub that does not answer is never shown as a problem, and availability reports (a log or hub that stopped answering) are not hub evidence and are never read.

Environment variables​

Empty values count as unset. The compose files pass every one of them to the services that read them.

Harvest​

VariableDefaultMeaning
HARVEST_VITRINE_INTERNAL_URLUnsetThe sidecar's internal listener, over HTTP/2 cleartext. Unset, transparent events' casts get unavailable and the Transparency tab can't create logs.
HARVEST_VITRINE_ADMIN_TOKEN_FILEUnsetA file with the sidecar's admin token, for the Transparency tab.
HARVEST_VITRINE_CONFIG_FILEUnsetThe deployment configuration. Unset, no event can be made transparent.
HARVEST_VITRINE_BUDGET_MS800How long a cast waits for its receipt in all.
HARVEST_VITRINE_WAIT_MS600The timeout of the sidecar's wait, below the budget, so that the sidecar answers before Harvest gives up.
HARVEST_VITRINE_BREAKER_FAILURES5The failures in a row that open the circuit breaker.
HARVEST_VITRINE_BREAKER_OPEN_SECS30How long the breaker stays open.
HARVEST_VITRINE_DEV_WITNESS_ADMINSUnsetDevelopment only: see below.

HARVEST_VITRINE_DEV_WITNESS_ADMINS is a comma-separated list of <witness internal URL>|<admin token file> pairs. When it is set, Harvest posts each log's enrolment note to those witnesses after a policy upload. In production, leave it unset: the witnesses' operators post the notes.

Running in development​

The sidecar and two witnesses run under the opt-in compose profile vitrine. The profile supplies the sidecar and log witnesses only. Before enabling an event, separately run the two app hubs, their witnesses, and two monitors named in .devcontainer/vitrine/deployment.toml, or replace their URLs, verifier keys and party labels with an explicitly provisioned infrastructure configuration using HARVEST_VITRINE_CONFIG_FILE. The checked-in development key files describe those identities; they do not start these additional services. The full Vitrine deploy/ stack is an example of the required lifecycle, but its keys must be copied from its actual configuration rather than assumed to match this file.

The hub operators must authorize the sidecar's enrolment signer, and the monitor operators must load each event's sealed policy into their monitor configurations before monitoring that event; an answering listener alone does not establish that it watches the event. Until that infrastructure is running, do not enable a production-like transparent event or claim complete verification. Missing hub or monitor responses remain pending or unavailable; the application never lowers profile requirements to make a local stack pass. Without the compose profile, the URLs above don't answer: transparent events' casts get an unavailable receipt, and the Transparency tab can't create logs.

  1. Build the image from a Vitrine checkout. It has every Vitrine binary, including the vitrine CLI:

    cd vitrine
    docker build -f deploy/Dockerfile --target runtime -t vitrine-log:dev .

    The meaning hashes in .devcontainer/vitrine/deployment.toml must be the image's:

    docker run --rm vitrine-log:dev cat /usr/local/share/vitrine-dev/meaning-hashes

  2. Start the services with the base stack:

    docker compose --profile base --profile vitrine up -d

    vitrine-setup copies the development keys and tokens of .devcontainer/vitrine/secrets/ into a volume, readable by the services' user only, and writes the services' configuration files. The services share the network namespace of the vitrine service:

    PortService
    8094The sidecar's public listener, also on the host at http://localhost:8094
    8095The sidecar's internal listener: http://vitrine:8095 for Harvest and Windmill
    8096, 8097Witness 1: public listener and admin listener
    8098, 8099Witness 2: public listener and admin listener

    The development sidecar runs with --dev-no-standby, since its PostgreSQL has no synchronous standby.

  3. The sidecar's configuration lists the election event databases that exist when vitrine-setup runs. After creating an election event, and before enabling its transparency, run the setup again and restart the sidecar:

    docker compose --profile base --profile vitrine up -d --force-recreate vitrine-setup vitrine-log

  4. In the admin portal, open the event's Transparency tab, enable transparency, and copy the draft policy to a file, for example draft.txt. Seal it as the development Board, whose key is in .devcontainer/vitrine/secrets/board.key, with the image's CLI:

    docker run --rm --network none --user "$(id -u):$(id -g)" \
      -v "$PWD:/work" -w /work vitrine-log:dev \
      vitrine policy seal draft.txt \
        --key .devcontainer/vitrine/secrets/board.key --authority board \
        --out policy.txt

    The development [sign] asks for the Board's signature only, which sealing adds. The vitrine policy check policy.txt checks the result; vitrine policy id policy.txt prints the policy's ID, in groups of four, for the Board to announce. Upload policy.txt in the Transparency tab. Harvest installs it in both logs and, with HARVEST_VITRINE_DEV_WITNESS_ADMINS, enrols the logs in both witnesses.

The keys and tokens in .devcontainer/vitrine/secrets/ are for development only. In production, the Board keeps its key offline, the operator's key is in the deployment's secrets, and every token is the deployment's own.

Tests​

From packages/:

  • Entries and statements. cargo test -p electoral-log --test vitrine_vectors checks step's encoders against Vitrine's vectors, copied in packages/electoral-log/tests/vitrine-vectors/ from Vitrine's profiles/election/ballots/v1/vectors, profiles/election/events/v1/vectors and testdata/styles. Copy them again when Vitrine's profiles change.

  • The ballot box and its queue. The ACCEPT_WITH_VITRINE contract tests, idempotent casting included, are in packages/electoral-log/tests/ballot_box.rs. They create a minimal copy of the sidecar's queue table, and run with the electoral-log PostgreSQL suite against a disposable PostgreSQL, as the electoral log's tests do: cargo test -p electoral-log --test ballot_box -- --ignored --test-threads=1 with the ELECTORAL_LOG_TEST_DATABASE_URL and ELECTORAL_LOG_PG_* variables of that suite. --test vitrine_grants checks the sidecar role's grants in the event databases that Windmill creates.

  • Harvest's receipt at cast. cargo test -p harvest services::vitrine runs the fail-safe tests against local stand-ins of the sidecar: stopped, slower than the budget, and answering garbage, each cast gets unavailable, and the breaker opens and closes.

  • Windmill. cargo test -p windmill --lib services::vitrine covers the configuration, the policy draft and its refusals, the statements and their hashes, and the own-ballot check of voters' forwards.

  • Against a running sidecar. windmill/tests/vitrine_sidecar.rs creates an event's logs, installs a sealed policy, enrols the logs in the witnesses, casts a ballot through the ballot box's queue, checks a voter's forward of its receipt, and logs and receipts the config and voting-opened statements. It needs the sidecar and the witnesses, and an event database that the sidecar's configuration lists. In the dev container:

    S=/workspaces/step/.devcontainer/vitrine/secrets
    WINDMILL_VITRINE_TEST_INTERNAL_URL=http://vitrine:8095 \
    WINDMILL_VITRINE_TEST_ADMIN_TOKEN_FILE=$S/admin.token \
    WINDMILL_VITRINE_TEST_DATABASE_URL=postgres://electoral_log:electoral_log@postgres:5432/<event database> \
    ELECTORAL_LOG_PG_VITRINE_QUEUE_ROLE=vitrine_queue \
    WINDMILL_VITRINE_TEST_WITNESS_ADMINS="http://vitrine:8097|$S/witness-1.token,http://vitrine:8099|$S/witness-2.token" \
    cargo test -p windmill --test vitrine_sidecar -- --ignored

Native queue and production verifier rehearsal​

For an isolated contract run, start Vitrine's vitrine-testkit example integration_server with a new absolute capability-file path. It creates its own vitrine-testkit-* PostgreSQL container, native log, witnesses, hubs, bootstrap hub and monitor listeners. Keep that process running while the checks run; stop it with SIGTERM or Ctrl-C to shut down its services and remove its own container. The owner-only capability file contains test credentials: never commit or publish it.

Build windmill's vitrine_sidecar test with --no-run, then use the exact executable path printed by Cargo:

cargo test --offline --manifest-path packages/Cargo.toml \
  -p windmill --test vitrine_sidecar --no-run
python3 scripts/vitrine-live-contract.py \
  /absolute/fresh-capabilities.json /absolute/vitrine_sidecar-TEST_HASH \
  /absolute/new-run-directory

The helper accepts only an explicitly supplied local development simulation, retains Step's Board/operator authority pins, and builds its deployment file from the running services' actual public keys and URLs. It runs both public and private contracts, refuses an existing output directory and keeps credentials out of its output. The public case exports the exact queued entry's original issued receipt, a witnessed record, the signed policy, acknowledgement and config/opened statement chains. The private case exports no private policy or read secret.

After building the ballot verifier and installing its Playwright Chromium, run its production receipt page against that public output:

node scripts/vitrine-browser.mjs packages/ballot-verifier/dist \
  /absolute/new-run-directory/public /absolute/browser-results

The browser runner checks a pasted chain and an uploaded receipt file at 1280 and 390 pixels, compares the offered policy ID with the fixture's independently supplied ID before pinning, verifies the voter's own ballot, rejects another ballot ID and a modified signed policy, and records screenshots plus proof results. It checks full-page overflow, runs axe over the receipt result, and refuses cookies, authorization or referrers on public proof requests. STEP_VITRINE_PLAYWRIGHT_MODULE can select a matching pinned Playwright installation in a browser container; the validated container uses Playwright 1.64.1. Every browser process and its temporary static listener shuts down when the script ends. Set STEP_VITRINE_RECORD_VIDEO=1 to retain actual browser clips for the public workflow.

The final package source also supplies deterministic full receipt-chain regressions for WAICT signature normalization. To compare the installed Step browser SDK with the compiled native verifier, build @vitrine/verify-wasm in a Vitrine checkout whose production source matches the recorded packages/vendor-npm/VITRINE_COMMIT, then run:

node scripts/vitrine-conformance-browser.mjs /absolute/vitrine-checkout \
  /absolute/new-conformance-results

This runner reads the ten shared chains from that exact Git revision, checks the installed SDK in Node and actual Chromium, and writes a screenshot plus the two backends' verdicts and WASM digest. Valid quorums survive extra bad known-witness lines, including malformed-length/time payloads; insufficient distinct valid signatures are refused. It makes no live-service request. STEP_VITRINE_PLAYWRIGHT_MODULE selects a matching installed runner when using the pinned browser container. Its static listener and browser shut down on completion.

This rehearsal uses synthetic accepted ballot rows and real native cryptographic receipts. It exercises the transactional queue and production independent-verifier page; it does not deploy the authenticated Step, Hasura/Harvest or Keycloak stack, or perform a complete encrypted voting ceremony. The voting/admin component suites and type checks cover those frontend contracts separately. Local party labels do not establish organizational independence, and an answering monitor listener does not establish that it subscribed to the newly created event.
