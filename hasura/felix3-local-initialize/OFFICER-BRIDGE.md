# Local staff certificate review in the existing Admin Portal

This optional overlay does not issue certificates or enable a signing action. It connects a generated, non-exportable key to the ordinary staff registry on the exact localhost test installation. Keep ordinary metadata, public environments and demo fixtures unchanged.

**How the two people use it**

1. The nominee signs in normally and opens the verified Initialize request in the Admin Portal, completes their own Gold setup and explicitly registers their signing key. While its certificate is pending, the nominee chooses to share presence with the responsible officer from that same dialog and original sign-in. Closing or hiding the dialog stops renewal; allow up to twenty seconds for the last observation to expire. There is no bearer or continuation token to pass to the other person.
2. In a separate browser session/profile, the officer already named by the permit signs into the _same_ normal Portal, opens the event's Signatures → Certificates and completes an independent, fresh Gold reauthentication. The officer reviews the request/nominee/Post and public CSR and can download the public PKCS#10 request. Only a qualified independently administered staff CA can issue the actual leaf. There is no terminal step for the nominee or officer in this Portal workflow. No local substitute certificate, PKCS#12, private key, or PIN will work. This change does **not** provide the separate CA issuance service.
3. The officer supplies just the genuinely issued public leaf, reviews its fingerprint and explicitly selects attach. It must correspond to the CSR, chain to the current staff trust for this event, have suitable signing usage and not be revoked. The actual registry insert and original enrollment attachment commit together under 2250. Gold expires in 60 seconds. If a new login is needed, review that CSR again in the new officer session. A lost response can be retried with the same reviewed leaf while the request, trust and same-session review remain valid; uncertainty is not evidence of success.

**Installation boundary (once per protected test environment, not once per nominee)**

- Install existing 2100 local marker, 2200/2210 self-setup, 2250 attachment and the local 2260 overlay, with the correctly nominated distinct officer. There must be exactly one _currently valid_ staff-signatures trust anchor for this event, one matching full, current and signed CRL, and an actual issuer for CSRs. The original attempt's authorization and key proof are immutable. After a lost session or ended request use the exact read-only overlay below. No raw user-specific digest, CSR or leaf is installed by hand.
- Enable the existing local feature, ordinary key setup and its validated realm keys/Hasura connection. Mount a root-owned read-only private installation file `harvest/attachment/registration.json` below the existing local descriptor. Its closed shape has `installation` (existing protected UUID), `database` (existing app database), and `registry_login` (a dedicated, established ordinary staff/audit writer with a name starting `felix3_local_`). No secret, user ID, key path, attempt ID, leaf, issuer, digest or role claim is read from this file.
- The browser must separately have `FELIX3_LOCAL_OFFICER_BRIDGE: true` **and** the existing exact verified localhost:3002/18080/18090 registration. Omission is off. The existing optional Hasura overlay supplies the four new actions, never a standalone public route or default production permission.
- The two new DB connections use the installed PostgreSQL Unix socket with peer authentication, not TCP, an administrative login or an env-controlled DSN. 2250 requires the verifier's actual PostgreSQL `system_user` to be `peer:felix3_local_attachment_officer`; mapping an unrelated OS user to that database role is insufficient. A deployment that cannot supply the required peer identities must not enable the bridge. The verifier and writer are different database logins and their runtime admission still enforces 2250's stricter ACLs. The registry writer must already support the real staff registration and audited transaction; this overlay does not give either login general write privileges.
- Keep existing 2200/2210/2250 access requirements. The only **additional** rights are schema usage on `felix3_initialize_bridge` for the setup Portal and officer verifier, plus execute for the setup login on `nominee_generation(binding,text)`, and for the verifier on `officer_scope(binding,uuid,uuid,text[],text[],timestamptz)` and `issuer_pins(binding,uuid,uuid,text[],text[],timestamptz)`. No new rights for the writer, PUBLIC, Hasura, a browser role or a person. Migration creates no grants to service identities; the installer intentionally provides these three routines. Failing the exact function allow-list prevents mounting. An absent or invalid attachment registration mounts none of the new routes. An invalid registration logs that the optional bridge is disabled; ordinary Harvest and the persisted HSM requirement remain in force. Do not enable the browser flag until the installed officer actions pass the private readiness check.
- This is an intentionally single-process local installation: presence and previous public CSR review are held in bounded memory and lost on restart. They are never persisted, shared across hosts, or substituted for independent JWT, live Post eligibility, DB permit or PKI checks. After a restart the two people must reopen/review the pending CSR. Do not adopt this as multi-replica production behavior.

## Resume the original key after signing in again

After 2270, open the verified Initialize request in the normal Portal. If the original sign-in or the request changed, select **Verify with Gold to resume**; return to the same request and explicitly select **Resume certificate review**. The short-lived presentation belongs to the independently verified ordinary Portal session. The server requires Gold after both completion of the original key and creation of the current request, and less than 60 seconds old. When it says ready, choose **I’m here for certificate review** separately. Neither viewing the page nor returning from sign-in creates presence, replays setup or enrolls a key. In a new session, after restart or once the five-minute presentation expires, repeat those recovery steps. Ordinary original-session presence is unchanged.

If the approval request expired or was replaced before certificate issuance, reopen the newer **waiting** Initialize request for the same Post. Its existing canonical request must explicitly refer to the same currently published ballot and installed scope. The original request must be closed without completing or executing, and the same nominee, independent officer and active permit still apply. This is a presentation of the original enrollment, never an approval of the old or new digest. The officer reviews and attaches the leaf for the existing key; approval of the current request is separate. A different publication, Post, applicant or officer is not recoverable by this flow; a fresh current approval and active authorized permit are prerequisites.

Install local 2270 after 2260. Keep the three existing 2250 authority actions and the officer's 2260 read-only grants. Replace the setup Portal login’s 2260 `nominee_generation(binding,text)` execute grant with exactly `nominee_recovery(binding,text)` on the same schema. There is no public grant and no function role/login change. The private helper resolving historical provenance is not executable by either browser-facing service login. Uninstalling 2270 restores original eligibility without touching the sealed registry, attempt or enrollment; unmount the optional attachment registration/actions first. The unsealed 2250 renewal policy must preserve the enrollment identity while allowing the later verified request after the original writer terminates; it must not move a sealed admission.
