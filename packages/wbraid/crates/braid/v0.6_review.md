Now, my review. I've verified the document against the actual code in all five areas. Overall: the direction is sound and largely feasible, and encouragingly, the vs_lift datalog already embodies several of the proposed changes (no batch, no Channel round, slot-based collision). But there are several places where the document is internally inconsistent or where the proposed change collides with how the current code (or the vs_lift code) actually works. I'll go section by section.

1. Messages, slots, and b4
1a. Single wire structure + "signature over the payload, no re-serialization"
Current reality: The signature is not over the payload. In message.rs, Message<C> is { sender, signature, statement, artifact: Option<Vec<u8>> }. The signature covers statement.ser() only; the artifact (the bulk data — ciphertexts, shares, etc.) is not signed, only its hash appears inside the Statement. Verification re-serializes the statement (self.statement.ser()) and verifies against that — exactly the re-serialization the document wants to eliminate.

The key tension the document itself flags (S3 compatibility): Today the design is actually well-suited to S3 precisely because the signed part (statement = a handful of hashes) is tiny and the large artifact is separate. That's what lets the http board push the big artifact to S3 and keep the signed statement inline. If the new "single payload that the signature is over" folds the bulk data into the signed payload, then:

the signature now covers megabytes, and
to verify anything you must fetch the full S3 object — you can no longer verify a message from its small inline part.
So I need to pin down the new layout:

Q1. In the new structure, are the "specific fields for that struct" the bulk artifact data (ciphertexts/shares), or are they still just hashes/metadata, with the bulk data remaining a separate unsigned-but-hash-committed blob (as today)? In other words, does the signature cover the large payload or not?

Q2. "No re-serialization to verify" implies verifying the signature over the received bytes of the payload. That removes the dependence on canonical/deterministic re-serialization (a real robustness win). Can you confirm the intent is: store the received payload bytes, verify the signature directly over them, and deserialize once for use — and that we therefore must keep the raw received bytes around (rather than reconstructing them)? This has implications for the digests-only storage model in §4.

1b. Slot computation
The slot idea (sender, type, and for mix-signatures the mix position) is feasible and is very close to what vs_lift already does in vs_lift/.../messages.rs via Message::collides(). But there's a concrete divergence:

Doc proposal: slot = (sender, type, mix_position), with mix_position encoded in the type enum (MixSignature(MixPosition)), validated against the Configuration (e.g. asking for the 5th mix signature fails with 2 trustees).
vs_lift reality: for MixSignature, collision is same sender && (input_hash == input_hash || output_hash == output_hash) — i.e. the slot is keyed by content hashes, not an explicit position. It never materializes a "position" for the signature.
These are genuinely different schemes with different properties, and they matter because b4 must also enforce slots (the doc says "message persistence must be aware of slots and enforce them"). b4 today already has a uniqueness constraint UNIQUE (board_name, sender_pk, statement_kind, batch, mix_number) in db.rs — i.e. a slot-like key built from small scalar columns. A position-based slot maps cleanly onto that; a content-hash-based slot would force b4 to index on hashes and understand mix chains.

Q3. Which slot scheme do we standardize on — the document's explicit (sender, type, mix_position) or vs_lift's (sender, type, content-hashes)? They can't both be the source of truth. My recommendation is the document's position-based scheme for the b4/storage slot key (cheap, scalar, enforceable by a SQL unique constraint), with the datalog still doing its content-hash chain validation on top. Do you agree, and if so, are you OK adapting vs_lift's collides() for mix signatures to a position-based key?

Q4. A trustee that knows it's signing "the mix at position k" needs k. In vs_lift, position is derived from the Ballots message's Vec<TrusteeIndex> ordering. Is the intent that mix_position is derived from the configuration/ballots selection (not self-asserted by the signer)? That's important for the "compute the slot from the Configuration" validation you describe.

1c. Ordering, write-once, and the internal inconsistency
This is the most important item to resolve. The document says two things that are in tension:

"apply the rule that once a slot is filled it is fixed" (first-writer-wins), and
"order ... could only have observable effects if slot collisions exist, and board clients are not enforcing write-once slots" (i.e. with write-once, order is irrelevant).
These only reconcile if a slot collision (two distinct messages for the same slot) is impossible in honest operation and treated deterministically when it occurs. But "first-writer-wins" is not order-independent: if a malicious trustee equivocates (signs two different mixes for the same slot) and a malicious b4 returns them in different orders to different clients, then "first wins" makes honest clients accept different messages → a fork. vs_lift avoids this entirely: collides() makes a collision a hard error that halts, computed over the whole message set, so the outcome is independent of order.

So the choices are:

(A) Halt-on-collision (vs_lift semantics): order-independent, detects equivocation, but a malicious board/trustee can DoS the protocol by injecting one colliding message.
(B) First-writer-wins (doc's literal wording): no DoS, but not order-independent and admits the fork above unless the "winner" is chosen by a deterministic rule (e.g. lexicographically smallest message hash) rather than arrival order.
Q5 (most important). Which semantics do we want when a slot genuinely collides — halt-on-equivocation (A), or write-once with a deterministic tie-break (B, e.g. lowest hash, not first-seen)? The document's "order doesn't matter" claim is only true under (A) or under (B)-with-deterministic-tiebreak; it is false under (B)-first-seen. I'd like to nail this down because it drives both the board-client logic and what b4 is allowed to do.

1d. Dropping the trustee's local order tracking
Removing last_local_board_id-style local ordering (see the "SECURITY CRITICAL" comment in trustee.rs) is feasible only if write-once slots are enforced deterministically as above, because today that local monotonic ID is exactly what prevents the board from rewriting history. Moving the guarantee into "write-once slots at the unified board client" is a reasonable relocation of the same invariant — but note it changes the threat model from "order is locally pinned" to "content is slot-pinned," and the equivocation question (Q5) is what makes or breaks it.

2. Unify local and remote board
Feasible and a good simplification. Today there are effectively three things: the Board trait (remote I/O, protocol/board.rs), LocalBoard (in-memory + persistence, protocol/board/local_board.rs), and two storage backends. Two concerns:

2a. Digests-only persistence for native
The doc wants the unified board to persist only digests (the wasm/IndexedDB model) and drop full-message storage (the native/SQLite model). The trade-off: native currently stores full messages so it can rebuild in-memory state from disk after a restart without the board. Digests-only means on restart the trustee must re-fetch the entire board from b4 and re-verify against stored hashes (this is what wasm does today).

Q6. Is full board re-fetch on restart acceptable for native/server deployments (boards can be large)? And is it acceptable that crash-recovery now depends on b4 being reachable (it can't tamper, since hashes verify, but it can withhold)? If yes, fine — just confirming we're knowingly trading storage/restart-self-sufficiency for uniformity.

2b. Interaction with §1a (the message-shape change) and S3
If the signature ends up covering the bulk payload (Q1 = "yes"), then digests-only storage plus S3 offload gets awkward: to re-verify on restart you'd re-fetch large objects from S3 and re-hash them. If the signed part stays small (Q1 = "no"), this all stays clean. This is the concrete reason §1a and §4-storage must be decided together.

3. Bootstrapping and the configuration message
Supplying the Configuration to the (renamed) SessionTrustee at construction rather than via update_bootstrap() is clean and feasible; it removes the special-case bootstrap path in trustee.rs. Encouragingly, vs_lift already treats configuration as a local ConfigurationValid fact rather than an on-board signed round — consistent with "config is initialization, not execution."

Two clarifications:

Q7. There's a terminology collision between two different "configurations": the private TrusteeConfig TOML (a trustee's own secret keys) and the on-board Configuration artifact (everyone's public keys). The doc's "require a configuration message on construction" refers to the latter. Can we agree on distinct names (e.g. TrusteeKeystore vs Configuration) to avoid confusion in the spec and code?

Q8. The doc suggests the configuration "could be part of the 'boards' table in b4 rather than the 'messages' table." Who delivers the Configuration to the SessionTrustee constructor in each setting — native (read from a file/the boards endpoint?) vs wasm (the browser operator pastes it, as the demo does today)? And does the board client still need it independently to verify signatures (it does — so it must be available to both the trustee and the board client at construction)?

4. The 'batch' field → parent/child boards
Removing batch from messages/predicates and pushing namespacing into b4 via parent→child boards is feasible and aligns with vs_lift (which has no batch anywhere). It's a non-trivial b4 change though. Today batch is woven through db.rs, handlers.rs, the messages schema, batch_count on boards, and demo_tool. Replacing it means a parent_board column and union-on-read.

Q9. Confirm the exact inheritance semantics: querying dkg_board/tally_1 returns that child's messages ∪ its parent's, but not sibling tally_2's. Single-level only (the doc says "single parent-child"), or arbitrary depth?

Q10. With slots now namespaced by board, the same ballot set mixed under two children is naturally separated. But the unified board client's "write-once across the union" must hold over parent+child together. Is a child allowed to ever write into a slot "type" that the parent also uses (I don't think so — DKG types live in the parent, tally types in children), or do we want b4 to reject a child message whose type belongs to the parent phase?

Q11. How does a SessionTrustee/Session address a child board — is the board name literally the path dkg_board/tally_1, and does the same trustee instance run DKG (on the parent) and each tally (on each child), or is a fresh session created per child?

5. New datalog (ascent + vs_lift rules)
This is feasible but is the biggest item, and I want to flag that it's larger than "swap crepe for ascent." The vs_lift rules encode a different protocol shape, not just a different engine:

Aspect	Current braid (crepe)	vs_lift (ascent)
Config	SignConfiguration→ConfigurationSigned→...SignedAll (on-board signed round)	ConfigurationValid local fact, no on-board sign round
DKG channels	Channel message (encrypted keypair + Schnorr PoK)	no Channel phase at all
Share/PK agreement	Shares, PublicKey + PublicKeySigned rounds	PublicKey only; agreement = all-equal else error
Batch	explicit BatchNumber in shuffle/decrypt	none
Indices	0-based TrusteePosition (+ special PM/Verifier indices)	1-based TrusteeIndex
Collisions	per-slot reject/idempotent	global error(String) → halt
Errors	typed DatalogError	error(String)
So adopting vs_lift means adopting its fewer-round DKG and its all-equal-or-error public-key agreement, dropping the *Signed aggregation rounds. The document calls this "minor changes," but at the protocol level it is a real change to the message set and the trust argument.

Q12 (important). Is the intent to adopt vs_lift's protocol shape wholesale (drop ConfigurationSigned/ChannelsAllSigned/PublicKeySigned rounds, drop the Channel phase, pubkey agreement by equality), or to keep braid's existing rounds and merely re-express them in ascent? The former is what vs_lift gives "for free" but is a substantive protocol change; the latter is more conservative but means meaningfully rewriting the vs_lift rules. Which way?

Q13. vs_lift has an Action::ComputeBallots(CfgHash, PublicKeyHash) and treats Ballots/the mixing-trustee selection as inputs. In braid, ballots are posted externally (protocol manager) and the mixing set comes with them. Who produces Ballots and selects the mixing trustees in v0.6, and is ComputeBallots relevant to us or a votesecure-only artifact?

Q14. Index base mismatch (0-based vs 1-based) and the special PROTOCOL_MANAGER_INDEX / VERIFIER_INDEX sentinels in braid have no obvious analog in vs_lift's 1-based trustee space. Do we standardize on 1-based throughout (and how do the protocol-manager/verifier roles map)?

Q15 (build/runtime risk). ascent is not yet a workspace dependency, and the vs_lift code uses ascent::ascent_source! + include_source! (a newer "composable rule sources" feature). Two things to verify early: (a) the ascent version we pin actually exposes ascent_source!/include_source!, and (b) ascent-generated code compiles to wasm32-unknown-unknown (the trustee runs in-browser). If ascent pulls in incompatible deps or relies on threads, that's a blocker we want to find now, not late. Want me to spike a minimal ascent-on-wasm build to de-risk this?

Q16. vs_lift ships stateright model-checking tests under #[cfg(test)]. Do we want to port/keep those (they're high-value assurance), and if so does that drag in stateright as a dev-dependency with its own wasm/native constraints?

6. Per-execution keys + symmetric-encryption removal
Conceptually clean and the vs_lift DKG (no Channel phase) already assumes it. But there are real coupling and security points:

6a. Coupling: this requires §5 and §3
Removing the Channel message only works if peers' share-encryption public keys are available elsewhere — the doc says "added to the configuration message." That means the on-board Configuration artifact must gain a Vec<share_encryption_pubkey> alongside the existing trustees: Vec<Verifier>. And it only composes with the datalog if we take the vs_lift channel-less DKG (Q12). So §6, §5, and §3 are one coupled change, not three independent ones.

6b. "Per-execution keys" vs "share-enc pubkeys in the configuration"
There's a tension to resolve:

Q17. If share-encryption public keys live in the Configuration artifact, then per-execution share keys imply a per-execution Configuration (a new config message per board/execution). But the doc also says deployments may "continue to use a single configuration file for all protocol executions." Those two are only compatible if "single config file" refers to the trustee's private keystore (reused inputs) while the on-board Configuration is still regenerated per execution. Can you confirm that the on-board Configuration is per-execution (so it can carry per-execution share pubkeys), and "single config file" just means a deployment opts to feed the same keypairs each time?

6c. Lost proof-of-possession
Q18 (security). Today the Channel carries a SchnorrProof — a proof of knowledge of the share-encryption secret key. If share-encryption pubkeys move into the (manager-produced) Configuration with no on-board PoK, we lose that proof-of-possession. For share encryption (not key aggregation) a rogue-key attack is less obviously exploitable than in threshold key aggregation, but I'd like an explicit decision: do we drop the PoK, or require trustees to supply a PoK to the protocol manager at config-assembly time (off-band)?

6d. Symmetric encryption removal — confirm nothing else uses it
Removing symm entirely is feasible: its only protocol use is encrypting the channel secret key (action/dkg.rs, encrypt_share_sk/decrypt_share_sk). With the Channel gone, the trustee no longer needs an encryption_key field at all. Just confirming we also drop encryption_key from TrusteeConfig/Trustee and the gen_trustee_config output.

Q19. In the wasm/browser setting, the doc says the browser is responsible for generating and persisting secret material across executions. Since the browser's storage is the user's responsibility, what's the intended UX/format for the operator to save and re-supply the per-execution signing + share-encryption keypairs (so a wiped browser can resume the same execution)? This affects the trustee.html flow and what the constructor expects.

Cross-cutting / possibly-missed items
Schema/version field. HttpB4Message carries a version string today; the new wire structure doesn't mention one. Recommend keeping an explicit schema/version for forward-compat. Intentional omission or oversight?
Timestamps are advisory. Statements carry a Timestamp that the signer controls; it can't be trusted for ordering or freshness. If the new "header.date" is meant for anything security-relevant, that won't hold. Assuming it's purely informational?
ciphertext_width (W). It lives in Configuration today and threads through the dispatch macro. vs_lift's rules don't mention W. Confirm W stays a Configuration field consumed by the action layer (not the datalog), so the datalog port doesn't need to know about it.
Halt semantics. vs_lift raises error(String) and expects execution to halt. Does "halt" mean the whole SessionTrustee stops, or just that board/child? And how is a halt surfaced/persisted so a restart doesn't just re-run into the same error silently?
Negation/recursion engine differences. crepe and ascent both do stratified negation, but ascent additionally supports lattices (which vs_lift uses via AccumulatorSet). No blocker, but the accumulator-as-lattice pattern is the kind of thing to unit-test carefully when porting.
Suggested sequencing (once the above is decided)
Because §1a (message shape) ↔ §4-storage, and §3+§5+§6 are one coupled protocol change, I'd propose: first lock down Q1/Q2 (wire) and Q5 (slot/ordering semantics), then the coupled config/datalog/keys change (Q12, Q17), with an early ascent-on-wasm spike (Q15) to de-risk the toolchain before committing.

The single most consequential thing to settle first is Q5 (collision/ordering semantics), because it determines whether "drop local order tracking" is even safe, and it exposes the one internal contradiction in the document. After that, Q1 (does the signature cover bulk data?) and Q12 (do we adopt vs_lift's protocol shape?) gate most of the rest.
