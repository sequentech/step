# braid v0.6 — Consolidated Specification

Status: DRAFT. This document is the forward-looking implementation reference for
braid v0.6. It consolidates and supersedes the Q&A-style decision log distilled in `v0.6_decisions.md`
(which remains the provenance record). Where this spec and that decision log disagree, THIS spec wins;
if this spec is silent, consult `v0.6_decisions.md`.

Related docs (provenance):
- `v0.6_decisions.md` — append-only DECISION log recording the resolved decisions and their rationale.

## 1. Scope & Vision

braid v0.6 is a **mixnet** trustee protocol: a set of trustees run a distributed key generation
(DKG), then shuffle (mix) and threshold-decrypt ciphertext batches, publishing all steps to an
untrusted bulletin board so the result is independently verifiable.

Three crates (workspace members; the `rnk` dev tool is out of scope here):
- **`braid`** — the trustee node, and therefore the core of the system: I/O, the message/artifact type
  definitions (§4), message verification, storage, the datalog brain (§7), the action layer (crypto
  operations), and the native + wasm bindings all live here.
- **`b4`** — the bulletin board trustees exchange messages through. It stores and serves **opaque
  bytes only** and never parses them, so it shares no protocol types with braid; its crate surface is
  the HTTP schema (`b4::api_types`) plus the server. The b4 server itself is untrusted (see Trust
  model, below).
- **`vsc`** (lib `cryptography`) — the low-level cryptographic building blocks (groups, ElGamal,
  shuffle proofs, DKG, signatures, serialization) that braid's action layer calls into.
- Scope is the **mixnet only** — no votesecure-specific artifacts (e.g. `ComputeBallots` is not ours).

The datalog rules that decide what is proven and what action each trustee may take (§7) originate
from a prior project, `vs_lift`; that code is ported in-tree and absorbed as braid's own `datalog`
module. It is not a separate crate or a standing architectural component — just provenance for one
module, noted where relevant (§7).

Trust model (summary; see §"Board client & b4" and the review for detail):
- **b4 (the bulletin board) is UNTRUSTED.** It provides availability only. It cannot forge messages
  (they are signed), and it cannot get away with silently rewriting history: two complementary
  mechanisms close that door together (§5.3) — the datalog's **total `collides()`** rule halts on two
  conflicting messages present in the same view, and the board client's **completeness gate** halts when
  a message it previously committed to is no longer reconstructible at all. Neither is a second,
  hand-maintained notion of a "slot" (§5.1) — both reduce to the one generated projection. So b4 can
  only ever cause an availability failure (withholding), never an accepted rewrite.
- **The trust anchor is OUT-OF-BAND.** The on-board `Configuration` message is self-signed by the
  manager key it embeds (circular); authenticity therefore comes from the operator/deployment
  validating, out of band, the manager signing pk (which also authenticates `Ballots`) and the
  trustee-peer signing pks.

### 1.1 Component data flow

The runtime data flow of a single trustee (the lens that cross-checks the section order):

```
b4/board --messages--> Board client --> Trustee --> datalog --> actions --> Board client --messages--> b4/board
      (ProtocolMessages)  (verify ->        (constructed                (produce      (build + sign
                          predicates,        with keys)      predicates  new artifacts; ProtocolMessages)
                          completeness,                      -> enabled  core crypto
                          storage)                           actions)    + width W)
```

- **Board client** verifies ProtocolMessages into predicates (+ bodies), runs the **completeness gate**
  against its persisted history (§6.3), and owns storage. It is the only persistence/completeness-aware
  layer — `collides()` itself is the datalog's job alone (§5.3).
- **Trustee** is constructed with its secret keys (§9) and operates on a single unified store,
  oblivious to whether that store is one board or a client-composed union of boards (§8): the union is
  a board-client concern, so the Trustee *code component* never sees it.
- **datalog** consumes predicates and yields enabled actions; **actions** run the core cryptography
  (parametrized by ciphertext width `W`) and emit new messages back through the board client.
- **M1 scope:** in the memory test the Board client is thin — NO b4 interaction and NO persistence;
  only the essential in-memory path required to make `test_protocol_memory` pass.

### 1.2 Within braid: functional core / imperative shell

- **The functional core** is `Trustee::step` (`trustee/mod.rs`): `fn step(&self, view:
  &MessageStore<C>) -> Result<Vec<ProtocolMessage<C>>>`. It takes the current view of the store as an
  input parameter and returns the messages it produces; it performs no I/O and holds no mutable
  protocol state between calls — only the fixed secret keys it was constructed with (§9). Called twice
  with the same view, it returns the same result.
- **The imperative shell** is `Session` + `BoardClient`: `Session::advance()` drives `update()` (fetch
  from b4) → `step()` (call the pure core) → `post()` (write back to b4); `BoardClient` owns the b4
  transport, the persisted anti-rewrite commitments (§6.3), and the in-memory store the core reads.
- Consequence: the core carries no memory of its own unconfirmed output between calls — it only ever
  sees what the shell hands it as `view`.

## 2. Milestones & Conformance

The build is driven by three existing integration targets in `tests/test_protocol.rs`, in order.
Each milestone adds exactly one layer of the risk stack; the named test is its acceptance gate.

### M1 — `test_protocol_memory` (core protocol, in memory)
`braid::native::test::protocol_test_memory::run` — full DKG → encrypt → mix → threshold-decrypt →
set-equality of plaintexts, for random `n_trustees`/`threshold`, parametrized by ciphertext width `W`.
Drives the `Trustee` directly over an in-memory `Vec<ProtocolMessage>` "board": the
harness relays each trustee's freshly produced messages to the others and iterates to a fixpoint.
**No b4, no persistence, no wasm, no I/O.** (The unified board-client abstraction is deferred to M2,
§6/§8.)

Requires (and is the acceptance gate for):
- new single wire structure + sign-over-received-bytes + body/`H(body)` split (§ Wire);
- `braid::messages` artifact/newtype updates (§ Message types);
- per-type **in-memory** storage collections (§ Storage), with no persistence in M1;
- datalog integration + generated `collides()` (§7);
- construction-time `Configuration` + share-encryption keypair, with no `bootstrap_msg`,
  `encryption_key`/symm, Channel phase, `batch`, `*Signed` aggregation rounds, or local order
  tracking (§ Keys/Config).

Explicitly NOT required by M1: predicate persistence, restart/diagnostic check, b4 server changes,
S3, wasm, parent/child boards.

### M2 — `test_protocol_http` (protocol against real b4)
Same end-to-end result as M1, but each trustee runs against a live b4 over HTTP.

Adds: the unified board client; b4 as a dumb, board-agnostic opaque blob store (no protocol schema,
no slot/uniqueness checks, no parent/child — board union is a **client** concern supplied out-of-band,
§8.2); predicate-only persistence backend (SQLite), with **full signature verification on every
retrieval** + restart reload + the **anti-rewrite completeness gate** against the persisted
committed set (§6.3); S3 body offload; version exact-match fail-fast across the b4↔trustee boundary.

### M3 — rebuild `dbg` as a wasm-capable mixnet emulator
Recreate the `src/bin/dbg` interactive simulator, now leveraging wasm so it can emulate a full mixnet
of browser-hosted trustees.

Adds: wasm bindings (wasm-bindgen), IndexedDB predicate-storage backend, in-browser `Trustee`,
interactive multi-trustee stepping; parent/child boards to run one DKG + multiple tallies (the full
mixnet setting). Operator secret-material supply is a construction input; any save/restore keyfile UX
is the caller's/demo's concern (nice-to-have, not blocking — see § Keys/Config, Q19).

Note on crate layout: message/artifact/newtype definitions live in `braid::messages`, braid's own
module, and braid is their ONLY consumer — b4 never interprets the bytes it stores (§8), so it needs
no protocol types at all. The message vocabulary is therefore an M1 foundation *inside braid*, and
"b4 first" reduces to **b4-the-server**, an M2 concern. Implementation evolves the existing `b4` and
`braid` crates in place on `feat/braid-0.6/main` — no new parallel crates; the code evolves in place
(git preserves prior versions for reference).

## 3. Wire structure & signing

Two forms cross the trust boundary: the **ProtocolMessage** (what travels over the network and lives on
b4) and, after verification, the **`(Predicate, Body)`** the protocol computes and stores on
(§4.2, §6.1). The **Statement** — the object that is signed and verified — is never explicit on the
wire and is never stored: both signer and verifier assemble it transiently, and the receiver
immediately projects it to a Predicate. In v0.6 the Statement is **not a Rust type**: it is realized
transiently as the `(head, H(body))` pair (§3.3), so there is no `Statement` struct or enum to
materialize, sign-and-store, or keep in sync.

### 3.1 ProtocolMessage (single protocol structure)
```
ProtocolMessage {
    sender,        // identifies the signer; the verify key binds sender.pk
    signature,     // over signed_bytes (§3.3)
    type,          // enum selecting the concrete head/body structs
    head,          // serialized head struct: date + common header fields + context hashes
    body,          // serialized body struct: the bulk (ciphertexts, shares, ...)
}
```
`head` and `body` are separate length-delimited fields, so `body` is a clean byte slice hashed
directly — no byte offsets or sub-sequences.

### 3.2 Statement & Predicate (assembled — never on the wire, never stored)
The **Statement** is the type-specific object that is signed and verified. It is assembled
transiently from the deserialized head + `H(body)` (§3.4 step 3); it is neither transmitted (§3.1
carries `head`/`body`, not the statement) nor persisted. Verification projects the Statement to a
**Predicate** by stripping wire-only metadata (§4.2), and the deserialized **Body** is stored under
that Predicate (§6.1). The retained pair is therefore `(Predicate, Body)` — there is **no persistent
`ProtocolMessage`/`{statement, body}` object**.

### 3.3 Signed bytes
```
signed_bytes = ser(Statement)
```
The **Statement is the single signed object** (canonical VSer serialization), consistent with
"the signed bytes are produced from the Statement". There is **no separate `domain_tag` and no
separate `type_tag`** — both are already carried inside the Statement:
- The Statement is a **type-specific** value (an enum with one variant per message type), so
  `ser(Statement)` already carries the **type discriminant**, so no separate `type_tag` is needed (it
  binds the type for free, preventing a wire `type`-flip / type-confusion attack).
- **Domain separation is the configuration hash, already inside every Statement.** Every message's
  context/in hashes include the **Configuration message hash** (`cfg_hash`) as their first element —
  the datalog encodes exactly this (every relation leads with `CfgHash`, and the prelude halts on
  `message.get_cfg() != configuration_valid.cfg_hash`). The Configuration message *is* the domain: it
  defines the setting (params, trustee/manager pubkeys). Because Configuration is **per-execution**
  (§9, Q17), `cfg_hash` is a *stronger* separator than a static `domain_tag` would be — it separates
  not just "this protocol" but "this specific execution", so a signature from one execution cannot be
  replayed into another (its `cfg_hash` won't match the target execution's bootstrapped context).
  - Bootstrap edge case: the Configuration message itself is the root and cannot reference its own
    hash. Its authenticity is anchored **out-of-band** at bootstrap (§9, Q8), not by a domain tag;
    its hash then becomes the domain for every subsequent message. The type discriminant still
    distinguishes a Configuration statement from all other types.
- Statement = the head fields (date, common header fields, context/in hashes incl. `cfg_hash`)
  **plus** `H(body)`. So the signature commits to `H(body)` (hence to the body, transitively) with
  the body NEVER re-serialized: `H(body)` is computed over the RECEIVED body bytes; only the small
  Statement is serialized (preserving the megabyte-scale re-serialization win).
- `sender` is NOT in the signed bytes; it is bound by WHICH verify key checks the signature
  (verify key = `sender.pk`).

Re-serializing the small Statement to verify is cheap and malleability-free under canonical + strict
VSer (§3.5) — which is exactly why we sign `ser(Statement)` directly rather than a hand-rolled byte
concatenation.

**Implementation (v0.6): the Statement is NOT a materialized type.** There is no `Statement` struct or
enum. `ser(Statement)` is realized concretely as `ser((head, H(body)))` — the already-defined per-type
**head** struct followed by the body hash — because every Statement variant would otherwise be exactly
`head + H(body)`, duplicating the heads. For **bodyless** messages (`MixSignature`) there is no `H(body)`
term, so the statement is `ser(head)`. A single generic helper (`statement_bytes(head, body_hash: Option)`)
produces these bytes for BOTH sign and verify, naming "what is signed" in exactly one place and
centralizing the byte layout (a correctness win a mere type alias would not give); no per-type
`Statement` alias is introduced. This is byte-identical to a hypothetical flat `Statement` struct because
VSer serializes structs and tuples as the flat concatenation of their fields.

### 3.4 Verification flow (ProtocolMessage → (Predicate, Body?))
1. `body_hash = H(body bytes)` over the RECEIVED bytes (no body re-serialization).  Skipped for
   bodyless message types (MixSignature).
2. Deserialize head (and body, when present).
3. Assemble the in-memory statement from the deserialized head + `body_hash` (transient local — the
   pair `(head, body_hash)`; no materialized `Statement` type, §3.3).  For bodyless messages the
   statement is the head alone (no `body_hash` term).
4. Verify the signature over `signed_bytes`.
5. Project the statement to a **predicate** (§4.2, stripping wire-only metadata: date, etc.) and
   return `(predicate, body?)`; the caller stores the body under the predicate (§6.1) when present.
   Bodyless types (MixSignature) return no body.  The statement is not retained — there is no
   persistent `{statement, body}` object.

Verification is **whole-message**: a message whose body has not been verified is not verified — there
is no partial verification. (This is what makes S3 offload a pure transport detail, §8: a black box
that returns the whole message, with no consequence for verification.)

### 3.5 Serialization assumption + action
`signed_bytes` safety relies on **VSer being canonical + strict** (exactly one byte encoding per
value; deserialize rejects non-canonical input), so re-serializing the head carries no malleability
surface. VSer was designed this way and is already depended on cryptographically.
**ACTION — OUTSTANDING:** re-audit VSer to confirm canonical + strict (verifying an existing
property, not a redesign). This has NOT been done; it is the top-priority item in §11, and until it
closes the argument above is an assumption rather than a checked fact.

### 3.6 Hashing properties
- **Integrity is transitive:** signature → statement → `H(body)` → body.
- **Cross-reference** (Mix→Mix, decryptions→plaintexts): everyone hashes the SAME received body bytes
  ⇒ no canonical requirement.
- **Agreement** (different senders, supposedly-identical value, e.g. PublicKey/Configuration):
  requires the body serialization to be canonical so equal values yield equal `H(body)`. Applies ONLY
  to agreement-bearing types (crypto objects with deterministic strand encodings).
- **No standalone `H(body)`, so no per-type domain separation is needed.** `H(body)` is never used as
  a bare hash: it is always a FIELD inside a predicate. In datalog it occupies a typed position in a
  type-specific relation; in the board client, bodies are keyed by the **full predicate** (not a
  projection or bare hash) inside a **type-specific collection** (§6). There is no "fetch whatever body
  has this hash" path, so cross-type body confusion cannot arise and the type is always fixed by
  context. (Hashing the type alongside the body is therefore optional — it could be done, but it buys
  nothing here.)

## 4. Message & artifact types (`braid::messages`)

Message/artifact/newtype definitions live in `braid::messages`, braid's own module. braid is their
only consumer: b4 stores each `ProtocolMessage` as opaque bytes and never parses one (§8), so no
protocol type crosses into the b4 crate. These types are an M1 foundation; the b4 *server* is M2, §8.

### 4.1 Statement is the central fact
The **statement** is BOTH what is signed AND what derives the datalog predicate. It binds
sender + context hashes + `H(body)`; `H(statement)` commits to `H(body)` (a two-level hierarchy):
- a statement's own `H(body)` field = that message's produced/"out" hash;
- the head's context hashes = references to OTHER messages' `H(body)` (its consumed/"in" hashes);
- the datalog chains `out_hash(prev) == in_hash(next)`.

Two hashes, hierarchical (Q-C): `H(body)` is body-content-only (so equal values from different
senders hash equally — required for agreement); the statement/predicate binds sender + context +
`H(body)` and is the tamper-resistant history unit and the keying mechanism.

### 4.2 Predicate (datalog relation)
Derived from the statement by stripping wire-only metadata (date, common header fields). Fully
contextual, e.g. `shares = (sender, configuration_hash, shares_body_hash)`; only the hash FIELD
(`shares_body_hash` / `pk_hash` / `in_hash` / `out_hash`) is body-content-only, while other fields
(sender, ...) carry context. Agreement fires when the body-derived field is equal across senders
(e.g. `pk_hash`) even though sender differs.

### 4.3 Indices & sentinels (Q14)
**1-based `TrusteeIndex`** everywhere (aligns with AccumulatorSet init-at-1). Configuration positions
are 0-based internally and mapped to 1-based (§9.6).
- **`PROTOCOL_MANAGER_INDEX`** — the sender identity for manager-authored artifacts (Configuration,
  Ballots), distinct from trustees `1..n`. Coupled to how Configuration/Ballots are authenticated
  (§9).
- **No `VERIFIER_INDEX`** — v0.6 has no in-band verifier mode; the verifier sits outside the mixnet
  path (a standalone next-version verifier is enabled by the retained "signatures kept for third-party
  verification" deferral, §11).

### 4.4 Artifact/body type list
Known types (from the memory test + the DKG→mix→decrypt
flow): `Configuration`, `Ballots`, `Shares`, `PublicKey`, `Mix`, `MixSignature`, `Plaintexts`. **No
`batch` field anywhere** — and, likewise, **no `mix_number`**: the `Mix` body is `(ciphertexts,
proof)` only. Mixing position is inferred by the datalog from the chain of `input`/`output` hashes
(§5.1, §7), and the shuffle's Fiat–Shamir domain is bound to `cfg_hash` + the (unique)
input-ciphertexts hash rather than to a position/id counter.
The per-type head/body field layout follows one rule (pinned in `braid::messages::wire`):
`head = predicate − sender − body_hash + date`. Reconstruction reverses it:
`predicate = (head − date) + sender + body_hash`.

## 5. Slots & `collides()`

The "slot" (write-once position) is **never materialized as data**. It is purely emergent from
`collides()`. There is no slot tuple, struct, or key to design; b4 enforces nothing security-relevant
(§8), so any b4 uniqueness constraint is a pure availability optimization.

### 5.1 collides() is a per-type, compiler-checked-total function
`collides(a, b)` is the **slot projection** of the full predicate — it drops the content hash and
keeps the discriminating context. It is defined per predicate type as a `Slot` impl dispatched over
the `Predicate` enum (via `enum_dispatch`):
- **default:** equality on `(sender, type)` (each sender fills one slot per type: Shares, PublicKey,
  Mix, ...);
- **MIX-SIGNATURE override (content-hash):**
  `same sender && (a.input_hash == b.input_hash || a.output_hash == b.output_hash)`. This is the only
  type where `(sender, type)` is not already a unique slot (a trustee signs every *other* trustee's
  mix, so it emits several). It reuses hashes already in the predicate — no new field. The comparison
  is **same-role**, so honest chained positions (`out_k == in_{k+1}`) do NOT false-collide, while a
  genuine equivocation at one position shares BOTH hashes ⇒ collides.
- **Ballots:** always collide (manager input).

`enum_dispatch` requires **every** variant to have a `Slot` impl, and `collides()` matches
exhaustively ⇒ it is **total** (can't-forget-a-type: adding a `Predicate` variant without a `Slot`
impl is a compile error). This is the single definition of "slot"; do not introduce a second one.

### 5.2 Semantics on collision: HALT-ON-EQUIVOCATION (Q5)
Two distinct messages projecting to the same slot ⇒ HALT. This is evaluated over the whole predicate
set, hence **order-independent** — which is exactly what makes dropping local order-tracking safe
(§6). A byte-identical resend is idempotent (same predicate key). Consequence: an equivocating
trustee or an adversarial b4 can DoS by injecting one colliding message — accepted (availability only;
b4 is untrusted, §8).

### 5.3 Where collides() runs, and its complement
`collides()` (§5.1) itself is evaluated at exactly **one** call site: the **datalog rule**. During
inference, if two predicates currently loaded as EDB facts fill the same slot with different `H(body)`
⇒ HALT. Because the store never evicts (§6.1), this alone already catches a colliding message served
*alongside* the original it conflicts with — both are live facts in the same view the moment either
is fetched, with no history/persistence involved at all.

It does NOT, by itself, catch b4 *replacing* a message: ceasing to serve one it previously committed to
in favor of a colliding one, with the original never served again. Then only the replacement is ever a
live fact — `collides()` has nothing to compare it to, because the original was never re-admitted in
*this* view (exactly what happens across a restart, whose store starts empty, and across a parent/child
union, whose store never itself directly observed the DKG board's messages either, §8.2).

That case is caught by a **complementary, non-`collides()` mechanism**: the board client's
**completeness gate** (§6.3), run once per `update()` — not per message, and not via `collides()` at
all. It checks plain **equality**: is every predicate in the durable **committed set** still
reconstructible from the current fetch? Within a slot, equality and `collides()` are complements — a
live entry is either equal to the committed predicate or collides with it, never neither (§5.1's
totality guarantees a `Slot` impl for every type) — so a committed predicate going missing is exactly
the signature of b4 now serving something different (or nothing) for that slot, without needing to ask
`collides()` at all.

Together the two mechanisms are a full anti-rewrite argument; neither alone is: `collides()` catches a
colliding message served next to its history, the completeness gate catches history disappearing in
favor of one. Both ultimately rest on the same slot projection (§5.1) — the gate through the
equality/`collides()` complement relation, not by calling `collides()` directly — so there is still only
one definition of "slot" backing both.

## 6. Storage model & persistence

§6 describes the **board client** — ONE component (what "storage" means in v0.6) with three
responsibilities:
- **(a) in-memory message store** — received messages held in per-type collections (§6.1);
- **(b) predicate persistence for anti-rewrite** — persist the predicates b4 has committed to (the
  pinned ground truth) and, once per `update()`, run the **completeness gate** (§5.3, §6.2–6.3): every
  committed predicate must still be reconstructible from the current fetch, or `step` does not run this
  cycle. The board client is both the *custodian* of the persisted set and the site of this gate (and,
  for a child board, **seeds** the set with the parent's predicates to extend it across the union, §8).
  The gate checks plain equality, not `collides()` — that stays the datalog's own job, guarding
  equivocation *within* a single in-memory view (§5.3); the two are complementary, not duplicates.
- **(c) b4 interaction** — fetch (feeding BOTH the in-memory store and persistence) and post messages.
  Detailed in §8 (schema, parent/child, union-on-read); the board client is the single
  parent/child-aware layer.

**Update-first & loop-back (LOAD-BEARING).** The board client is the ONLY path by which a message
enters a trustee's view — it is the trustee's whole outside world. A message a trustee *produces* has
**no local effect until it loops back from b4**: `step` returns messages, the board client posts them,
and only a *subsequent fetch* (verify → persist digest → admit to memory, §6.2) makes them visible to
inference. The runtime cycle is therefore **update-first**: (1) the board client updates from b4;
(2) the trustee's `step` runs inference over that view and returns new messages; (3) the board client
posts them; back to (1). The trustee never advances on its own unconfirmed output. Two consequences:
- **Recomputing an artifact that is not on the board is fault-tolerance, not a fault.** A failed post
  (or a message b4 never served) leaves the slot unfilled, so the next cycle recomputes and reposts —
  no collision, because nothing is there to collide with. A failed update just means `step` is not
  called that cycle.
- **The only halt path is a dishonest b4.** Once a trustee has observed its own artifact at least once
  (so it is in the committed set, §6.2), b4 withholding it on any *later* read is caught immediately by
  the completeness gate (§6.3) — before the trustee ever gets a chance to recompute a replacement. If
  b4 instead serves the original *alongside* a later recomputed one, the datalog's own `collides()`
  (§5.2–§5.3) catches that pair once `step` runs. Either way it is safe and detectable, adding no trust
  in b4 (trusted only for availability, §8): it never silently proceeds.

### 6.1 Per-type in-memory collections
Storage is a set of **per-type collections**, deserialized and type-safe (hand-written, with an
exhaustive `match` for insert/lookup that gives the same compile-time totality as `collides()`):
```
per type T:  HashMap<FullPredicate, Body>
```
- **KEY = the full predicate** (the datalog relation tuple: sender + context/in hashes + out hash
  `H(body)` + type). Content-addressed: a caller must name the exact hash, so the store can never
  return a body the datalog did not authorize (a safety gain).
- **VALUE = the body only** (the hash is not repeated in the value — it is already in the key).
- The **keyset IS the ascent EDB**: storage → datalog is a per-type copy of keys; keys are relation
  tuples.

Write-once lives ONLY in datalog: the store is a pure content-addressed set; equivocating messages
have distinct keys ⇒ both stored ⇒ both become relations ⇒ `collides()` halts (§5). The store itself
performs no overwrite/slot check — that would duplicate the single slot definition (§5.1) and add
nothing for safety.

### 6.2 Persistence = predicates only (single design, native + wasm)
Persist the **predicates (the keys) only** — never full bodies. A predicate is a whole tuple whose
fields include the pinned `H(body)`; that hash is a *field* of the predicate, not a separately stored
artifact. Bodies are transient/in-memory: they are only ever obtained by re-fetching the **whole
message** from b4 (never a body independently), and **every fetched message has its signature verified
on every retrieval** (§3.4). Persistence is an *additional*, durable anti-rewrite layer — never a
substitute for signature verification. One backend trait, two media:
- **native:** SQLite;
- **wasm:** IndexedDB.

This is the single persistence design for both platforms. (M1 uses `NoOpPersistence` = no persistence;
SQLite persistence is M2, IndexedDB persistence is M3.)

### 6.3 Restart & the anti-rewrite completeness gate
Restart obeys the same **update-first** rule as steady state (§6); it simply *reloads* the predicates
persisted before the crash into the board client's **committed set**.

The **anti-rewrite** check is a **completeness gate**, run once per `update()` — not per message, and
not `collides()` (§5.3). On every `update()`, the client first verifies and admits every fetched message
(§3.4, §6.1) with no collision check at admission time; once the whole fetch is admitted, it checks
that every predicate in the committed set is still present, by plain equality, among what was just
admitted. If any committed predicate is missing ⇒ HALT — b4 is no longer serving what it once
committed to for that slot, whether it replaced the message or is merely withholding it; `step` does
not run this cycle. Otherwise the predicate set persists, grows with anything newly admitted, and
`step` runs over the resulting view (where the datalog's own `collides()` still guards equivocation
*within* that single view, §5.3, for the complementary case of two colliding messages served together).

Checking equality here rather than calling `collides()` is deliberate, not incidental (§5.3): within a
slot the two relations are complements, so "is the committed predicate still reconstructible" and "does
nothing live collide with it" are the same question, asked as one cheap set-containment test over the
whole fetch instead of a per-message comparison threaded through admission.

Body integrity needs no separate step. Every re-fetched message is fully verified (§3.4): `verify`
recomputes `H(body)` from the received bytes into the predicate's content hash and checks the
signature. So a tampered body cannot slip through — either its (adversary-forged) signature fails, or,
if the trustee genuinely committed to that slot, the differing `H(body)` yields a differing predicate,
and the *original* committed predicate is then simply absent from the fetch ⇒ the completeness gate
HALTs.

**Persistence and re-execution prevention are distinct mechanisms.** Persisted predicates are exactly
the b4-sourced (looped-back) ones; their sole job is **anti-rewrite** — pinning, irreversibly, which
`H(body)` b4 has committed to for each slot. They are **not** a defense against b4 *dropping* an output
that was never yet committed (that is availability): a dropped/never-served message that was never
admitted has no persisted predicate, its slot reads unfilled, and the trustee recomputes it (the
fault-tolerance of §6) — the completeness gate says nothing about a predicate that was never committed
in the first place, only about one that was and has since disappeared. **Re-execution is prevented by
update-first + loop-back, not by persistence**: on restart the trustee re-observes its own
already-posted outputs *from b4* (which, having looped back before the crash, are also the ones
persisted), so the negation guards are satisfied and completed actions are not re-enabled.
Crash-recovery therefore depends on b4 **reachability** — never-yet-committed and dropped ⇒ recompute
(safe); previously-committed and now missing or replaced ⇒ HALT (safe) — never on b4 **honesty**.

## 7. Datalog (ascent) integration

The datalog is the protocol "brain": port vs_lift's `ascent_logic` module wholesale. Source in-tree at
`crates/braid/vs_lift/trustee_application/ascent_logic/` (`prelude` in `mod.rs`; `dkg.rs`, `mix.rs`,
`decrypt.rs`; `messages.rs`; `utils.rs`; `protocol.rs`). DISCARD the actor driver
(`top_level_actor.rs`, `handlers/`) — braid's Sessions/Trustee is the driver (§1). Re-wire
imports to the `vsc` crate (`cryptography`) for `CryptographicHash`, `Context`, and W-generic crypto.

### 7.1 Program structure
Three relation kinds and three matching rule kinds:
1. **input** relations — facts injected from the outside world via `relation message(Message)`;
2. **intermediate** relations — derived by rules (accumulators, positions, chains);
3. **output** relations — `relation action(Action)` and `relation error(String)`, read by the trustee.

Composed with `ascent::ascent! { include_source!(prelude); include_source!(dkg_infer);
include_source!(mix_infer); include_source!(decrypt_infer); }`. Every referenced type must be
`use`-imported at the `include_source!` expansion site (ascent sources are token templates).

### 7.2 `Predicate` replaces vs_lift's `Message` (the adapter seam)
One of the deliberate adaptations made while porting (`datalog::mod`): the input relation carries
our typed `Predicate` enum where the vs_lift source had a `Message` enum — both are exactly
contextual hash facts (§4.2), so the swap is direct. The whole messaging evolution (§3) is the
adapter: `ProtocolMessage{head,body}` → verify → `Predicate` → datalog → `Action`. Variants (all
cfg-first): `ConfigurationValid`, `Shares`,
`PublicKey`, `Ballots`, `Mix`, `MixSignature`, `PartialDecryptions`, `Plaintexts`. Loading the per-type
storage keyset into the `message` relation IS the EDB load (§6.1).
- **Typed hashes:** the hash fields are typesafe newtypes (`CfgHash`, `PublicKeyHash`, …, each a
  distinct type over `CryptographicHash`), so positions cannot be confused (matches §3's
  typed-statement principle).

### 7.3 `collides()` and the cfg-domain rule live in the prelude
- `Message::collides(&self, &other)` is the single slot definition (§5): equal ⇒ not a collision
  (dedupe); differing discriminant ⇒ no collision; default ⇒ same `sender`; **MixSignature** overrides
  with `same sender && (in==in || out==out)`; **Ballots** always collide. The prelude halts on it:
  `error("duplicate message …") <-- message(m1), message(m2), if m1.collides(m2);`. `collides()` is
  expressed as per-type `Slot` impls dispatched over the `Predicate` enum (`enum_dispatch`), so
  totality is compiler-checked (§5.1).
- `configuration_valid` is bootstrapped from `Message::ConfigurationValid` and the prelude halts any
  message whose `get_cfg() != context cfg_hash` — the datalog embodiment of "cfg_hash is the domain"
  (§3.3). See §9.7 for how each trustee establishes its own `ConfigurationValid` fact.

### 7.4 Halt = `error(String)`, per-board
`composed_ascent_logic::run(messages) -> Result<Vec<Action>, String>`: run the program; if the
`error` relation is non-empty ⇒ `Err` ⇒ HALT this board (§5.2, §10). Error conditions are specific
(`pk mismatch`, `ciphertexts mismatch`, `unexpected input ciphertexts`, `duplicate message`) per the
prelude warning "error condition relations should be specific". Halt scope is per-board (§8).

### 7.5 Actions = the boundary to the crypto/action layer
`relation action(Action)` yields the compute steps the Trustee executes: `ComputeShares`,
`ComputePublicKey`, `ComputeMix`, `SignMix`, `ComputePartialDecryptions`, `ComputePlaintexts`
(+`ComputeBallots`, test-only). Each `Action` carries the **full predicate context** it acts on, so
the board client can fetch the exact bodies it needs (§6.3). The action layer — NOT the datalog —
consumes **W** and the vsc crypto; the datalog sees only opaque hashes (**W-agnostic**, §10). The DKG
is channel-less and public-key/plaintext agreement is by equality (all-equal else HALT); no `*Signed`
counting barriers (see `v0.6_decisions.md` Q12).

### 7.6 Production vs testing composition (Q13)
- **Production:** `composed_ascent_logic` = `prelude + dkg_infer + mix_infer + decrypt_infer`. `Ballots`
  is an INPUT posted by the manager; `Action::ComputeBallots` never fires.
- **Testing:** `composed_ascent_logic_testing` adds one rule
  `action(ComputeBallots) <-- public_keys_all & configuration_valid & !ballots` to self-close the
  DKG→mix→decrypt loop. Keep `ComputeBallots` ONLY in the test composition. (braid's M1 harness posts
  `Ballots` as a manager input like production; the extra rule is only for stateright
  self-generation.)
- **stateright** mixnet tests (Q16) are `[dev-dependencies]`, `#[cfg(test)]`, **native-only** — they
  never compile to wasm, so impose no wasm constraint. Which mixnet tests to port is still open.

### 7.7 `AccumulatorSet` (utils) — adopt as-is
A relation-column helper that gathers per-trustee values indexed by trustee: `new(init)` (at index 1),
`add(v, index)`, `extract() -> Vec<T>` (index order). Fixed capacity `MAX_TRUSTEES + 1` (tied to `braid::messages::newtypes::MAX_TRUSTEES`, currently 8); **panic-
guarded uniqueness** (same index/different value, or duplicate value/different index) — a defense that
overlaps `collides()`'s guarantee. Used by `shares_acc` / `public_keys_acc` / `partial_decryptions_acc`
and the `*_all` barriers. Low risk, model-checked (cross-cutting 5); keep `MAX_TRUSTEES ≥` deployment n.

### 7.8 ascent toolchain (Q15 — build-verified, §Findings)
```toml

```
Sequential `ascent!` only (no `par` ⇒ no rayon/dashmap/crossbeam ⇒ no threadless-wasm risk); the
`wasm-bindgen` feature routes ascent's `instant` timing dep through the browser clock (no-op native).
`ascent_source!` + `include_source!` compose the rule sources; compiles to

## 8. Board client & b4 (b4 board-agnostic; client-side board union)

b4 is an **UNTRUSTED** bulletin board, trusted for **availability only** (Q-B); it may be treated as an
adversary. It does NO slot logic and NO verification — a dumb (possibly adversarial) blob store. All
collision / tamper / write-once semantics are enforced by trustees (§5–§6). b4 can therefore cause
UNAVAILABILITY, never accepted tampering. b4 knows only independent **boards** — it has NO notion of
parent/child lineage or unions; a tally-over-DKG **union** is composed entirely by the trustee's board
client (§8.2), keeping every security-relevant relationship out of untrusted b4. Stack: Axum +
sqlx/SQLite (WAL) + S3/LocalStack.
(This whole section is **M2**; the `braid::messages` TYPES are M1, §4.)

### 8.1 b4 storage schema
- **`boards`**: NO lineage. b4 has no `parent_board` column and no notion of parent/child — boards are
  independent; the union is client-side (§8.2).
- **`messages`**: no `batch` (Q12) or `mix_number` (§4.4). b4 stores each `ProtocolMessage` as opaque bytes
  keyed by `(board_name, monotonic id)`, plus `version` (§10.1); it does NOT interpret message
  contents and enforces no uniqueness constraint (nothing security-relevant — the slot lives only in
  datalog `collides()`, §5). At most it may dedupe *byte-identical* resends by wire digest as an
  availability optimization; trustees dedupe/halt on read regardless.
- The `inline_data BLOB` / `s3_key` split stays: the small **head** may stay inline while the large
  **body** is offloaded to S3. This is a **pure transport detail** (Q-A/Q-B) with NO verification
  consequence — fetching returns the whole message; verification is whole-message (§3.4).

### 8.2 Board union — a CLIENT concern (Q9–Q11)
The parent/child relationship is **not on b4**; it is reconstructed **client-side**, because it is
**security-relevant**: running a tally means the trustee *approves* running over a specific prior DKG
session, and anti-rewrite across that union is load-bearing (below). Since b4 is untrusted, it must not
be the source of that relationship — so, exactly like the Configuration trust anchor (§9.3), the
`(child, parent)` board pair is supplied to the board client **out-of-band at construction**, never by
b4.
- **Layering.** The Trustee *code component* is oblivious — it runs on one unified store (§1.1).
  The trustee *as an entity* approves the union (out-of-band). The **board client is the union-aware
  layer**: told the `(child, parent)` pair, it reads from BOTH boards and merges them into the single
  store the Trustee sees; writes go only to the **child** (tally) board.
- **Single hop** (Q10 item 1): a tally unions exactly ONE parent (its DKG board); no recursive chains.
  Siblings are isolated (tally_1 never unions tally_2); the relation is one-directional
  child → parent.
- **Multiple tallies over one DKG = the union mechanism (this replaces `batch`).** One DKG can back
  many tallies, each a separate child board reusing the same DKG data (different ciphertext sets). This
  is why sibling isolation is *required*, not merely convenient: all tallies of a DKG share the same
  `cfg_hash` (§9.5), and the slots are coarse — `Ballots` collides per configuration and
  `Mix`/`PartialDecryptions`/`Plaintexts` are per-sender (§5.1) — so two tallies' predicates in one
  session/store would false-collide (tally_2's `Ballots` vs tally_1's) ⇒ spurious HALT. Each tally is
  therefore its **own session + own committed store**, seeing only `dkg ∪ its-own-child`; the shared
  DKG parent is seeded into each (anti-rewrite-protected, below) while the children stay isolated. The
  old per-`batch` slot partitioning is thus subsumed by the board-union boundary.
- **Union content** (Q10 item 4): the parent contributes the DKG OUTPUT the tally consumes —
  `Configuration` (the per-execution domain, reused by tallies, §9.5), `Shares`, and `PublicKey` — so
  the tally's composed datalog re-derives `public_keys_all` and runs mix/decrypt while the DKG rules go
  inert (their negation guards are satisfied by the unioned parent messages). The tally board itself
  carries only `Ballots`/`Mix`/`MixSignature`/`PartialDecryptions`/`Plaintexts` under that same
  `cfg_hash`; a foreign `cfg_hash` trips the datalog cfg-domain halt (§7.3), so the union's authenticity
  rests on signatures + `cfg_hash`, never on b4.
- **Anti-rewrite across the union** (Q10 item 3, LOAD-BEARING): the board client **seeds its committed
  predicate set with the parent's predicates**, supplied at construction (out-of-band, like the
  `(child, parent)` pair). The seed MUST be the trustee's **own committed digests from its DKG
  session** — its own memory of what it accepted during the DKG — NOT a fresh b4 re-fetch. A bare
  re-fetch could only trust whatever b4 serves on first read (trust-on-first-use), blind to a rewrite
  that predates the tally's construction; seeding from the trustee's own digests is what actually
  forbids a child board from rewriting its parent's DKG history. The tally still re-fetches the parent
  in `update()` — it needs the parent **bodies** to re-derive the joint key and its decryption secret
  (§7.5/§9.4), which the predicate seed does not carry — but those fetched messages are checked against
  the seeded baseline by the **completeness gate** (§6.3): a seeded DKG predicate that is no longer
  reconstructible — because b4 now serves something different for that slot — ⇒ HALT before the tally's
  `step` ever runs. (If instead b4 serves the seeded original *alongside* a conflicting message, the
  datalog's own `collides()` catches that pair once `step` does run, §5.3.) This extends the §1/§6
  write-once/anti-rewrite invariant across parent ∪ child, and — crucially — b4 **cannot influence
  whether the union is established at all**, because the client does it from its own construction
  inputs, not from anything b4 reports. Any conflicting unioned message is caught by one of the two
  mechanisms (§5.3); no "type-partitioning" rule is needed.

### 8.3 create-board & namespacing (Q10 item 7)
The MANAGER creates the tally board as a **plain, independent board** on b4 (b4 has no `parent`
parameter) and posts `Ballots` to it; it conveys the tally-over-DKG relationship — the `(child,
parent)` pair — to the trustees **out-of-band** (§8.2), the same channel that carries the Configuration
trust anchor (§9.3). Board creation is **untrusted namespacing**: trust flows from the Configuration +
signatures + the client-seeded parent digests, not from a board's existence or name. A human/tooling
convention (e.g. `dkg1/tally1`) MAY encode the lineage in the board *name* for legibility, but b4
enforces nothing by it; a bad create is an availability concern only.

### 8.4 Halt scope (Q10 item 9)
Per-session. A halt in a tally session halts THAT tally's Trustee only — not the DKG session,
not sibling tallies. Sessions (each a board client + its union) are independent failure units
(§10 halt).

### 8.5 Non-security transport conveniences (Policy Notes)
- **Monotonic cursor** (Note 1): b4 MAY expose a monotonic sequence so a trustee fetches incrementally
  ("everything after N"). It is b4-side TRANSPORT METADATA only — NOT signed, NOT in the predicate;
  nothing security-relevant may depend on it (a dishonest cursor → missing/re-fetched messages =
  availability, already accepted). It cannot certify completeness (the withholding limit of Q5).
- **Duplicate dedupe** (Note 2): two wire messages with identical predicate but different wire bytes
  (differing only in predicate-excluded head fields — date/version/signature) are protocol-identical.
  The store is a SET keyed by predicate; inserting a present predicate is an idempotent no-op. A dumb
  b4 may store all copies; the trustee dedupes on read (b4 dedupe is an optional optimization).

## 9. Keys, Configuration & bootstrap

### 9.1 Two distinct config objects (Q7)
- **`TrusteeConfiguration`** — the trustee's OWN private keystore (secret key material; may hold more
  than keys). In a wasm/browser setting this file may not exist at all.
- **`Configuration`** — the on-board public protocol artifact: parameters + everyone's **signing**
  pubkeys + everyone's **share-encryption** pubkeys + the manager pubkey.

### 9.2 Configuration is per-execution and always fetched from b4 (Q8, Q17)
The on-board `Configuration` is regenerated PER EXECUTION and carries BOTH signing pubkeys AND
share-encryption pubkeys. Any real trustee (native AND wasm) ALWAYS fetches it from b4 — it is NEVER
pasted in a real run. `cfg_hash = H(Configuration body)` is the per-execution domain (§3.3). ("Single
config file" only means the same `TrusteeConfiguration` inputs may feed successive runs; the on-board
Configuration is still per-execution.)

### 9.3 Trust anchor is out-of-band (Q8)
Configuration comes from untrusted b4, and its self-signature is by the manager pk *inside* it
(circular) — so the self-signature is provenance/integrity only, NOT the root of trust. At bootstrap
the operator/deployment validates **out-of-band**: the manager signing pk (which also authenticates
`Ballots`) AND that the peer trustees' signing pks in the Configuration are genuine. The demo's
"paste" flow is a demo affordance for the `TrusteeConfiguration` (secrets), NOT for the on-board
Configuration.

### 9.4 Secrets supplied at construction (§6d, Q18, Q19)
- The Trustee takes the **signing sk** + the **share-encryption sk** as CONSTRUCTION inputs
  (secret side). Their public sides live in the Configuration.
- **No symmetric encryption (§6d):** `TrusteeConfiguration`/trustee carry no `encryption_key`, and
  there are no `encrypt_share_sk`/`decrypt_share_sk` helpers — there is no Channel and no share-key
  wrapping (§7/Q12).
- **No on-board proof-of-possession** of the share-enc sk (Q18) — deferred; safe under all-n
  halt-on-problem DKG (a rogue key only ⇒ halt, never silent compromise).
- **Q19 out of scope:** how a caller generates/persists/re-supplies these secrets across browser
  sessions is the CALLER's concern (above our wasm API). Trustee API = secrets-in-at-construction.

### 9.5 Execution unit = the DKG parent board (item 6)
The per-execution **signing** keypair is fixed in the shared Configuration and REUSED by every child
tally of that DKG; the **share-encryption** keypair is per-DKG-execution. So "an execution" == the DKG
parent board, and child tallies inherit its key context (§8).

### 9.6 Indices & sentinels (Q14 — see §4.3)
1-based throughout. `PROTOCOL_MANAGER_INDEX`: manager identity = the manager signing pk in the
Configuration + the sentinel (`get_trustee_position` maps the manager pk → `PROTOCOL_MANAGER_INDEX`;
`Ballots` is verified against `protocol_manager`). No `VERIFIER_INDEX` (§4.3).

### 9.7 Bootstrap flow
The Configuration is supplied at construction. Per trustee:
1. Fetch + out-of-band-validate the Configuration (§9.2–9.3); compute `cfg_hash`.
2. **Locally inject** `ConfigurationValid(cfg_hash, threshold, trustee_count, self_index)` into its
   own datalog `message` relation. This is a SELF-SCOPED fact (its 4th field is `self_index`), derived
   from the accepted Configuration body — NOT a board message. It enables that trustee's
   `ComputeShares` action (§7.3).
3. There is **NO config-signing board round**: config acceptance is implicit — the first thing a
   trustee posts (`Shares`) is signed and carries `cfg_hash`, so posting Shares IS the observable
   config acceptance (the folded-in attestation from the aggregation decision).
M1 (`test_protocol_memory`): the harness builds a Configuration (params + n trustees' signing +
share-enc pubkeys + manager pubkey) and constructs each Trustee with its `(signing sk,
share-enc sk)` + that Configuration; no `bootstrap_msg`, no symm, no Channel.

### 9.8 Construction dependency chain = acceptance boundary
The Configuration enters via the **board client**, not the Trustee directly:
- The **board client** is constructed from **connection input** (b4 endpoint + board name for HTTP; a
  pre-seeded board for M1 memory). A POST-CONDITION of successful construction is that it **contains a
  Configuration message** (fetched from b4, or seeded in memory). "No Configuration ⇒ board-client
  construction fails" is the invariant.
- The **Trustee requires a constructed board client**, so it **transitively requires a
  Configuration**. A constructed Trustee therefore *is* that trustee's acceptance of the
  Configuration — construction is the acceptance boundary. (Step 2's `ConfigurationValid` injection is
  done by the Trustee, which supplies `self_index` and reads the Configuration held by its
  board client.)
- **Where a future review/accept UI would go:** between board-client construction (Configuration
  retrieved) and Trustee construction (acceptance). The out-of-band validation of §9.3 occupies
  exactly this gate today; a UI acceptance step would slot into the same place with no structural
  change.

## 10. Cross-cutting (version, timestamps, W, halt)

### 10.1 Version (schema/format) — exact-match fail-fast
Sole purpose: catch serialization skew between a separately-deployed b4 and trustee. **No backward
compatibility** — versions must match EXACTLY; mismatch = hard error, no negotiation. Must cover
everything crossing the b4↔trustee boundary (wire head/predicate + body); one bump per format change.
**NOT a security field** (b4 untrusted, Q-B; a lying b4 = availability only). The existing b4 `version`
column and the `api_types` version string on the HTTP boundary are retained, re-scoped to this.

### 10.2 Timestamps (`header.date`) — informational only
Purely informational in v0.6; **nothing consumes it**. NOT security-relevant — the datalog and the
trust argument MUST NOT depend on it (it is one of the wire-only fields stripped when deriving the
predicate, §4.2). Retained for a possible FUTURE freshness policy ("too old, refuse") — out of scope.

### 10.3 W (`ciphertext_width`) — invisible to the datalog
The datalog sees only OPAQUE ciphertext hashes (opaque width). W stays a `Configuration` field
consumed by the ACTION/crypto layer (§7.5), never a datalog relation/term. This is what lets the
ported datalog rules stay W-agnostic while braid keeps W-genericity.

### 10.4 Halt — not persisted/surfaced in v0.6
No durable "halted" flag; on restart a trustee may re-run into the same error ("keep failing"). SAFE
because `collides()`, the completeness gate, and the error rules are all deterministic (§5.2–§5.3,
§6.3): a re-run re-detects the same problem and halts again, never silently proceeds. Only cost = no persistent
operator-facing halted record — accepted for v0.6 (see §11 for the deferred surfacing/persistence).

## 11. Deferred / out of scope for v0.6

These are banked rather than built in v0.6, ordered by priority. All but the first are *features*
explicitly out of scope; the first is an outstanding **verification** task that v0.6's signing design
already depends on and that has not yet been performed:

- **Audit VSer for canonical + strict serialization (§3.5).** Highest priority: this confirms an
  assumption v0.6 *already relies on* rather than adding anything. Two properties rest on it —
  `signed_bytes = ser(Statement)` is malleability-free only if VSer admits exactly one byte encoding
  per value and its deserializers reject non-canonical input (§3.3, §3.5); and **agreement** hashing
  needs the same property, since `PublicKey`/`Configuration` bodies from different senders must hash
  equally to be compared (§3.6). VSer was designed this way and is already depended on
  cryptographically, so this is verifying an existing property, not a redesign — but the verification
  has not been done. Scope: re-read `vsc::utils::serialization::{variable, fixed}` for any encoding
  admitting more than one representation of a value (length-prefix width, `Option`/enum tags,
  padding) and for deserializers that accept input a canonical serializer would never emit (trailing
  bytes after a complete value, over-wide prefixes); then add round-trip and reject-non-canonical
  tests pinning the result. Natural companion: those modules carry
  `#[allow(clippy::arithmetic_side_effects)]` with a "pending fuzzing" note, so fuzzing the
  deserializers covers the same surface. Until this closes, §3.3's malleability argument and §3.6's
  agreement property rest on an unverified assumption.
- **Use naor-yung ciphertexts for input ballot**. Follow the votesecure design, naor-yung ciphertexts are stripped as part of the first mixer's computations: naor-yung -> strip ->
elgamal -> shuffle -> elgamal input to next mixer.
- **Per-tally domain separation for Fiat–Shamir transcripts.** `domain_label` (§3.3) is keyed on
  `cfg_hash`. Since a single DKG/`Configuration` now backs multiple tallies via the child-board union
  (§8.2), sibling tallies share the same `cfg_hash` and therefore the same transcript domain — the
  separation the removed `batch` field once provided is gone. In practice sibling tallies still differ
  by their (distinct) ciphertext-set hashes, which already feed the shuffle seeds, so this is not a
  known vulnerability; but a belt-and-suspenders fix would re-introduce an explicit per-tally
  identifier. Design hook: carry an identifier on the `Ballots` message and propagate it into
  `domain_label`, so every child tally derives a distinct proof-transcript domain. Not a v0.6 concern.
- **Standalone independent verifier** (Q14): v0.6 has no in-band verifier mode; a future verifier
  checks a completed board out-of-band, enabled by the retained-signatures deferral above.
  Feasibility analysis of reusing Verificatum's `vmnv` as that verifier — same mix-net, same
  Terelius–Wikström shuffle proof, but an incompatible Fiat–Shamir transcript — see
  `VERIFICATUM.md`.
- **Retain message signatures for third-party dispute resolution** (Q5/Q-C). v0.6 is detect-and-halt
  only; PROVING equivocation to a third party would require retaining the two conflicting signed
  messages, not just their predicate digests. (The digests-only persistence, §6.2, is compatible — a
  future dispute mode would additionally retain the signed bytes.)
- **Share-encryption key proof-of-possession** (a Channel Schnorr proof, Q18). Add (on-board, or
  off-band at config assembly) if a complaint/disqualification / partial-threshold-blame mechanism is
  ever added.
- **Halt surfacing/persistence** (§10.4): a durable halted flag + operator-facing report.
- **Interactive anti-rewrite demonstration** (dev/demo tooling): an equivocation control that posts a
  conflicting, validly-signed message for a slot a trustee has already committed to, so an operator can
  observe the detect-and-halt boundary (§6.3) live — including across a restart, where the persisted
  committed set (§6.2) is what catches it. Detection itself is covered by tests; this is purely an
  observability aid. Design hook: needs per-trustee halt isolation, and (for a tally-phase slot after a
  restart) reconnecting the specific prior board so its persisted commitments reload.
- **wasm operator keyfile save/restore UX** (Q19): a demo-page nice-to-have; the trustee API
  stays secrets-in-at-construction.

## 12. Forward concerns (post-v0.6, non-binding)

Where §11 banks deferred *features* (each with a concrete design hook), this section records *standing
concerns and possible future directions*. They are **non-binding** for v0.6: none changes the trust
model, and none gates a milestone. They are captured here only so they are not lost, again ordered by priority:

- **Assurance — port the vs_lift stateright model-checking tests.** The datalog (§7) draws on
  vs_lift's `stateright` model-checking harnesses, which carry real assurance value; v0.6 uses only the
  inference rules (§7.6). Bring the model checks over "at some point" as native-only `#[cfg(test)]`
  model checks (§7.6 records the composition + the still-open question of which mixnet tests to port).
  Timing open; gates nothing. Effort analysis: see `ASSURANCE.md`.
- **Performance.** v0.6 prioritizes correctness and clarity; performance is a first-class *future*
  concern (large ballot sets; browser-hosted trustees in M3). The pre-refactor `braid` implementation
  is a valuable reference and a source of reusable, already-tuned code (git preserves it). Constraints
  to respect: `ascent` runs sequential-only (no `par`, §7.8), so parallelism lives in the action/crypto
  layer (rayon natively; `wasm-bindgen-rayon` in the browser). Optimize from benchmarks, not
  speculation. Infrastructure note: `braid/Cargo.toml` carries a `jemalloc` feature (gating
  `tikv-jemallocator`) as both a higher-performance native allocator and a profiling / introspection
  tool; it is not yet wired into the runtime but is available for use when optimization work begins.
- **Incremental fetch (monotonic cursor).** v0.6 board clients re-fetch and re-derive from the board
  on each update (idempotent — the store is a set keyed by predicate). b4 MAY expose a monotonic cursor
  for "everything after N" (§8.5 Note 1); using it is a pure **transport optimization**, never
  security-relevant, and it cannot certify completeness. Deferred: v0.6 does a full re-fetch; the
  cursor is a later optimization. This applies per board, including a union's DKG **parent** (§8.2),
  which a tally re-fetches every cycle even though it is static after the DKG — an obvious
  fetch-once / cursor target.
- **b4 role evolution for internal diagnostics (bounded, non-security).** v0.6's b4 is a dumb,
  untrusted blob store: NO checks and NO computed metadata — the dumb-store invariant is load-bearing
  for the trust model (§8), and the only diagnostic is trustee/board-client-side at the fetch boundary
  (§5.3, §6). A future, *bounded* relaxation MAY let b4 optionally perform checks and/or compute
  metadata **purely to improve failure diagnostics** (ideally gated to internal/test builds), provided
  nothing security-relevant ever depends on it — safety must continue to rest solely on the trustees
  (§5–§6). Recorded as a possibility only; v0.6 keeps b4 fully dumb.
