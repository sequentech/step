# braid v0.6 — Decision Log

Append-only provenance record for the decisions consolidated in `v0.6_spec.md`.
Where this log and the spec disagree, the spec wins.

---

Q1. In the new structure, are the "specific fields for that struct" the bulk artifact data (ciphertexts/shares), or are they still just hashes/metadata, with the bulk data remaining a separate unsigned-but-hash-committed blob (as today)? In other words, does the signature cover the large payload or not?

The hashes/metadata would be under "- fields for hashes that set the context for that struct",
these would correspond to what in the current version is called the statement. My suggestion for the new structure was aimed at great simplicity and clarity, and no reserialization. This would be achieved because 1) There is no separation between artifact and the bulk of the message, there is just the payload which is all of it serialized, and 2) because everything is serialized the signature is over the payload, there is no need to then include the artifact
hash in the statement, nor the need to verify that the hash of the artifact indeed matches the hash for the artifact in the statement. Of course, these objectives may run into

"the design is actually well-suited to S3 precisely because the signed part (statement = a handful of hashes) is tiny and the large artifact is separate. That's what lets the http board push the big artifact to S3 and keep the signed statement inline."

"to verify anything you must fetch the full S3 object — you can no longer verify a message from its small inline part."

which you rightly raise. The intent of the s3 mechanism is and should be an _internal implementation detail_ about how to send large amounts of data on the network. It should have
no consequences for verification. In other words, it should act as a black box where you put
your message in and get the message out, and do not care that this is achieved by splitting things, those are transport considerations that should not affect verification. So, what I'm answering really is that verification pertains to a message as a whole, because messages whose
artifact has not been verified are _not_ verified. There is no point in verifying a message partially because the signature over the statement has been verified, because we would still
require the artifact bytes to compare the hash to what was in the statement. This is the picture
I had in my head, but of course, I may be missing something and am not addressing the concerns in the analysis. Please let me know if this is the case.

Q2. "No re-serialization to verify" implies verifying the signature over the received bytes of the payload. That removes the dependence on canonical/deterministic re-serialization (a real robustness win). Can you confirm the intent is: store the received payload bytes, verify the signature directly over them, and deserialize once for use — and that we therefore must keep the raw received bytes around (rather than reconstructing them)? This has implications for the digests-only storage model in §4.

Yes, this is the intent. The fact that the signature is over a large amount of bytes does not
matter because the hashing of large amount of bytes has to be done anyway. You either do it
when constructing the hashes and then signing that, or when passing the bytes directly to the
signature algorithm, which will internally hash itself. The hashing of large number of bytes
(the current artifact) will be done anyway.

Q-A (the key one): Do you agree the public-key-agreement case forces an artifact-content hash, and are you happy with "board client computes the content hash of the trailing artifact byte-range" (option b) rather than re-introducing a signed self-declared pk_hash that must be match-verified (option a)?

Good point, we need the content hash to construct datalog predicate (relations). I'm not too happy with using offsets and dealing with byte subsequences. Perhaps we can revisit my original goal of not serializing on verification. I had not factored in that what's being serialized is a small amount of simple data, this should be trivial to
compute. So, perhaps we can use this fact the following way:

WireMessages retain a single structure at the wire level, something like
        - sender
        - signature
        - type: enum indicates what specific structs (2) are in the payload
        - head: serialization of a specific head struct
            - date
            - other common header fields
            - fields for hashes that set the context for that struct
        - body - serialization of a specific body struct
            - fields for bulk of the message

Protocol messages are type-specific correspond to WireMessages but in a concrete form that can be used to compute protocol steps. Protocol messages contain
- a type-specific statement, built from the WireMessage head _plus_ the hash of the WireMessage body
- a type-specific body field, which is the deserialization of the WireMessage body.

When constructing a protocol message from a WireMessage, the hash of the ProtocolMessage
body is used to construct the protocol message statement. Because Statements are computed from protocol messages, they use the content hash directly in their construction, there is no need to compare two separate hashes coming from different places. They key that allows this to work is that Statements are never explicit in WireMessages, they are assembled before and after. The other purpose that Statements have (as in the current implementation), is to derive Predicates (datalog relations). 

In summary a WireMessage transforms into a protocol message by 1) Computing the body
hash, 2) Deserializing the head and body (used in 1 to compute the hash), 3) Assembling the statement from the deserialized head and body hash, 4) Verifying the signature on the WireMessage against the statement serialization (small price to pay), 5) Constructing the protocol message struct with the statement and the deserialized body.

Finally, a predicate can be derived from a statement directly, which should involve simply removing the unnecessary parts contained in it that datalog logic does not care about (like for example date and other wire related meta data)

DECISION: Q-A (message structure & verification) — AGREED

Wire vs protocol layers
- WireMessage (single wire structure):
    - sender
    - signature
    - type: enum selecting the concrete head/body structs
    - head: serialized head struct (date, common header fields, context hashes that set the context for this struct)
    - body: serialized body struct (the bulk of the message)
  head and body are separate length-delimited fields, so body is a clean byte slice — it is hashed directly, with no byte offsets / sub-sequences.
- ProtocolMessage (type-specific, concrete form used to compute protocol steps):
    - statement: assembled from the deserialized head PLUS H(body)
    - body: the deserialized body struct
  Statements are NEVER explicit on the wire; they are assembled by both signer and verifier. Therefore there is no comparison of two separately-supplied hashes.

Statement is the central fact: it is BOTH what is signed AND what derives the datalog
predicates. The signed bytes are produced from the Statement; the predicate is produced
from the Statement (by stripping wire-only metadata).

Verification flow (WireMessage -> ProtocolMessage)
  1. Compute body_hash = H(body bytes), over the RECEIVED bytes (no body re-serialization).
  2. Deserialize head and body.
  3. Assemble the (in-memory) statement from the deserialized head + body_hash.
  4. Verify the signature over the signed bytes.
  5. Construct the ProtocolMessage from the statement + deserialized body.
- Predicates are derived from the statement by stripping wire-only metadata (date, etc.) the datalog does not care about.

Signed bytes (agreed)
- signed_bytes = domain_tag || type_tag || ser(head) || H(body)
    - ser(head) re-serializes the typed head. This is cheap (head is small, simple, fixed-layout).
    - The body is NEVER re-serialized: H(body) is computed over the RECEIVED body bytes. The big
      re-serialization win (megabytes of ciphertexts) is preserved regardless.
    - type_tag binds the message type (prevents a type-confusion attack from flipping the wire `type`).
      (Equivalently, a type-specific Statement enum variant carries the discriminant in its serialization.)
    - domain_tag gives cheap domain separation (complements per-execution keys, §6).
- Statement remains the single object that is signed AND used to derive predicates.

ASSUMPTION (re-serializing the head is safe BECAUSE): VSer is canonical and strict — exactly
one byte encoding per value, deserialize rejects non-canonical input. This is by design and is
already depended on for other cryptographic reasons in this project. Re-serializing the head
then carries no malleability surface (no second wire encoding can deserialize-then-reserialize
to the same signed bytes).
  ACTION (v0.6): re-audit VSer to confirm canonical+strict serialization. This is uncovering /
  verifying an existing design property, NOT a redesign — VSer was built to be canonical.

Hashing properties
- Body integrity is bound transitively: signature -> statement -> H(body) -> body. Tampering the body changes H(body), changes the assembled statement, fails the signature.
- Cross-reference hashing (Mix->Mix, decryptions->plaintexts): everyone hashes the SAME received body bytes => no canonical requirement.
- Agreement hashing (different senders, supposedly-identical value, e.g. PublicKey): requires the body serialization to be CANONICAL/deterministic, so equal values yield equal H(body). This applies ONLY to agreement-bearing types (PublicKey, config), whose bodies are crypto objects with deterministic strand encodings.

Binding
- The verify key binds sender.pk. type is bound via type_tag.
- (Open follow-up) sender.name binding and the precise canonical-body type list to be confirmed when detailing §5/§6.

Consequence noted for later (Q-B/Q-C)
- head is small and can stay inline while body is offloaded to S3. b4 does NO slot/verification logic (see Q-B); the head/body split is purely a transport optimization. H(body) is the natural content hash carried inside the statement/predicate.

DECISION: Q-B (b4 trust model) — AGREED

- b4 is UNTRUSTED and trusted for AVAILABILITY ONLY. It may be treated as an adversary.
- b4 does NO slot logic and NO verification. It is a dumb (possibly adversarial) blob store.
- All collision / tamper-resistance / write-once semantics are enforced by the TRUSTEES, because
  they cannot assume anything about b4.
- Implications:
    - An adversarial b4 may serve conflicting (equivocating) messages for the same logical
      position, or serve different bytes on restart. Trustees detect collisions on READ and HALT
      (vs_lift model). b4 can therefore only cause UNAVAILABILITY, never accepted tampering.
    - This is the same mechanism that lets us "drop local ordering" safely; the precise collision
      semantics (Q5 in the review) still need to be pinned down.

DECISION: Q-C (hashes, persistence, keying) — AGREED

Two related (hierarchical) hashes, NOT one
- H(body): body-only content hash. Used by the datalog for chaining and AGREEMENT (equal values
  from different senders must yield equal hashes, so it cannot include head/sender/date). It is a
  FIELD carried inside the statement/predicate, and it self-certifies fetched body bytes.
    - Clarification: the PREDICATE itself is fully contextual (e.g. shares = (sender,
      configuration_hash, shares_body_hash)); it threads context through. Only the hash FIELD
      (shares_body_hash / pk_hash / in_hash / out_hash) is computed from the body content alone.
      Agreement fires when that body-derived field is equal across senders (e.g. pk_hash), while
      other fields such as sender still differ.
    - A statement's own H(body) field = that message's "produced/out" hash.
    - The head's context hashes = references to OTHER messages' H(body) (its "consumed/in" hashes).
    - The datalog chains out_hash(prev) == in_hash(next), both equal to H(body_prev).
    - To prevent cross-type body confusion under a bare-hash fetch, H(body) is domain-separated by
      type (hashing the type alongside the body preserves agreement and blocks type confusion).
- The statement/predicate (which binds sender + context + H(body)): the tamper-resistant history
  unit AND the keying mechanism. H(statement) commits to H(body) (hierarchy).

Persisted ground truth = the PREDICATE (serialized), not a bare hash
- The persisted object must contain ALL data the collides() function needs, so it cannot be just a
  hash. It is the PREDICATE: sender (as an integer index) + the datalog-necessary data (context
  hashes and H(body)) + type; it EXCLUDES date and other common wire-header fields that are
  extraneous to protocol logic.
- On restart the predicates are deserialized and collides() is evaluated on them (potentially in
  datalog, as vs_lift already does).
- The persisted predicates are self-trusted: they were signature-verified before being persisted.
  b4 cannot touch the local store, so it cannot rewrite history.

collides() is a per-type function, not a data structure
- Adopt vs_lift's collides() semantics directly (e.g. most types collide on (type, sender);
  Ballots always collide; MixSignature collide on sender && (in==in || out==out)). Each predicate
  type has its own collides() implementation. No uniform "slot tuple" is imposed.

Keying / retrieval unified with the ground truth
- The statement/predicate is itself the keying mechanism for its body: retrieval is contextual
  ("give me the body of this type, for this configuration, with this content hash") rather than a
  bare "give me whatever has this hash". This unifies retrieval with tamper-resistance and
  collides() under one object.
- H(body) remains the self-certifying content field: a fetched body is checked against the H(body)
  carried in the trusted predicate.

Body availability & verification flow
- Bodies are fetched on demand from b4 (availability only) and self-certified against the H(body)
  in the trusted predicate; no signature re-verification is needed for bodies.
- New (not-yet-persisted) messages from b4: full signature verification over the statement, then
  collides() check against persisted predicates, then persist the predicate.

Signatures: detect now, prove later
- Simplest thing first: signatures are NOT persisted. Trustees DETECT and HALT on misbehaviour; we
  have not previously attempted to PROVE misbehaviour.
- NOTE (future): third-party-verifiable dispute resolution (proving equivocation) would require
  RETAINING the two conflicting signed messages, not just their predicate digests.

DECISION: Q5 (collision / ordering semantics) — AGREED: HALT-ON-EQUIVOCATION

Semantics
- When a slot genuinely collides (two distinct messages for the same slot), it is a HARD ERROR that
  HALTS (vs_lift semantics, option A). Chosen as the safest and simplest option.
- Rationale: agreement fundamentally requires hash equality (if the hashes did not match, trustees
  could not agree on anything), so a genuine collision is by definition a protocol violation.

Order-independence (why ordering can be dropped)
- Protocol computation is over the unordered message SET (datalog fixpoint); collides() is evaluated
  over the whole set and any collision halts. The outcome therefore depends only on the SET of
  messages seen, not on their arrival order.
- Honest trustees never equivocate, so honest messages have no colliding sibling; only an equivocator
  (or a malicious b4 injecting a conflict) creates a collision. "First-seen" is thus unambiguous for
  honest messages, and among an equivocator's two branches the order is immaterial (either branch
  triggers a halt once the other is seen).

CONSEQUENCE — §1d: DROP the trustee's local order tracking
- Remove the "SECURITY CRITICAL" local monotonic id (last_local_board_id) and all local order
  tracking. The invariant relocates from "order is locally pinned" to "content is slot-pinned +
  equivocation halts", backed by the persisted predicate set (Q-C).
- Tamper argument: persisted predicates are trusted local history (verified before persisting, and
  b4 cannot touch the local store). A later conflicting message collides() -> halt, so b4 cannot
  silently rewrite history; it can only cause a halt or withhold (availability), never an accepted
  rewrite.

Accepted trade-off: safety over liveness
- A single equivocating message (from a Byzantine trustee, or one colliding message injected by a
  malicious b4) can HALT the protocol (a DoS), even when an honest threshold exists. This is the
  deliberate safe-by-default choice and matches vs_lift. Halting to investigate is preferred over
  producing a possibly-wrong result.
- Detection only (per Q-C): halt on detection; proving the equivocation to a third party would
  require retaining the two conflicting signed messages.

POLICY NOTES (amendments to Q-B / Q-C / Q5) — AGREED

Note 1: b4 ordering as a STRICT optimization (non-security)
- b4 MAY expose a monotonic sequence/cursor so a trustee can fetch incrementally ("give me
  everything after N; I already have up to N-1").
- Guardrails that keep this out of the security model:
    - The sequence number is b4-SIDE TRANSPORT METADATA only; it is NOT part of the signed wire
      message and NOT part of the predicate.
    - Nothing security-relevant may DEPEND on it. A dishonest cursor can only cause missing or
      re-fetched messages (an availability effect already accepted), never a safety violation,
      because computation is set-based and the trustee's authoritative state is its persisted
      predicate set, not b4's counter.
    - Caveat: because b4 can withhold, a decision point needing completeness (e.g. being sure both
      halves of an equivocation are seen) cannot rely on the cursor claiming "you are caught up".
      This is the same withholding limit as Q5, not a new one.

Note 2: duplicate (non-colliding) messages -> DEDUPE BY PREDICATE (non-security)
- Definition: two wire messages with an IDENTICAL predicate but different wire bytes. They can only
  differ in head fields EXCLUDED from the predicate (advisory date, a version field, the signature),
  which are non-protocol by construction; so the two are protocol-identical.
- Policy: the persisted store is a SET keyed by predicate. Inserting a message whose predicate is
  already present is an IDEMPOTENT NO-OP (keep existing, drop the duplicate). Since only the
  predicate is persisted (Q-C), there is nothing to disambiguate.
- Three insert outcomes (making the Q5 boundary explicit):
    1. new predicate, no slot conflict          -> insert
    2. predicate already present (identical)     -> idempotent dedupe (this note)
    3. same slot-key but predicate differs       -> HALT (Q5 equivocation)
- Minor (non-security): a dumb b4 stores all copies; the trustee dedupes on read. b4 may dedupe as
  an optimization, but correctness does not rely on it.

Q12 (adopt vs_lift protocol shape) — AGREED
- YES: drop the Channel phase entirely.

- YES: halt-on-collision (already locked in Q5).

Aggregation (the resolved "no aggregation" item) — AGREED, drop all *Signed rounds
- FACT ESTABLISHED FIRST: there is no single "all-n-signed" object today. The wire Statement enum
  has only PER-TRUSTEE signature messages (ConfigurationSigned, ChannelsAllSigned, PublicKeySigned,
  PlaintextsSigned, MixSigned). The *SignedAll predicates are OutP — locally-derived datalog
  conclusions each trustee reaches after collecting all n individual messages; they are NEVER
  posted. So an external observer must already read the board and collect n messages either way.
- Each *Signed round is a sequential counter/barrier: per-trustee X Signed message -> inductive
  SignedUpTo(n) chain -> XSignedAll barrier predicate that gates the next phase.
- Two flavours, both preserved without the barrier:
  * Attestation (ConfigurationSigned; ChannelsAllSigned): a trustee signs an artifact it did not
    produce. Agreement survives via hash-bound participation — the first thing each trustee posts
    (Shares) is signed and carries cfg_h, so posting Shares IS the config acceptance. Config signing
    messages therefore disappear entirely (fold into Shares), not merely change shape.
  * Re-derivation (PublicKeySigned; PlaintextsSigned): the current design is already agreement-by-
    equality — each confirming trustee independently RE-DERIVES the artifact, checks it matches the
    posted hash, and signs that hash. vs_lift keeps the independent re-derivation and drops the
    asymmetric producer/signer roles + the counting barrier, using a symmetric all-equal check.
- ADOPTED SHAPE (symmetric): all n trustees independently compute and post the FULL artifact
  (PublicKey, Plaintexts); datalog enforces agreement by equality (all hashes equal else HALT).
  No designated trustee-0 producer; no SignedUpTo/SignedAll counting.
- Message-count effect vs current: Config -> FEWER (n sig-only messages become 0). PublicKey and
  Plaintexts -> same count, but the n-1 confirming messages carry the full artifact instead of
  hash+signature.
- SIZE TRADE — ACCEPTED: full artifact posted by all n means n copies of the artifact (a real n×
  multiplier on plaintexts, the largest object). We ACCEPT this for simplicity; not optimizing now.
  If plaintext size ever forces it, the equality semantics are separable from size: confirming
  trustees could post H(artifact)+signature (artifact stored once / fetched from b4) with the same
  security (independent re-derivation + all-equal). Deferred; not expected to be needed.
- External-consumer question CLOSED: no new aggregated certificate is required; "read the board +
  check equality/threshold" is already the status quo. Downstream trust argument restated in
  equality/counting terms (vs_lift stateright models already encode this — see Q16).

Q17 (per-execution Configuration) — AGREED
- The on-board Configuration is PER-EXECUTION and carries BOTH signing pubkeys AND share-encryption
  pubkeys. "Single config file" refers only to a deployment feeding the same TrusteeConfiguration
  inputs each run; the on-board Configuration is still regenerated per execution.

Q18 (share-encryption proof-of-possession) — AGREED (drop for now)
- Drop the Channel's Schnorr proof-of-possession of the share-encryption secret key for now; moved

  complaint/disqualification mechanism (partial-threshold blame) is ever added.

Consequence to confirm later (follows from dropping Channel)
- symm (symmetric encryption) has no remaining protocol use; drop encryption_key from
  TrusteeConfiguration/trustee and from key generation (Q6d / §6d).

SCOPE / VISION: v0.6 = braid "body" + vs_lift "brain" (mixnet only)

Guiding thesis (answers "why not just use vs_lift entirely?"): vs_lift is a model-checked protocol
brain, not a deployable trustee. v0.6 keeps braid's deployment skeleton and swaps in vs_lift's
simplified protocol + datalog + mixnet model tests.

KEEP FROM BRAID (the "body"):
  a) High-level structure: Sessions / SessionTrustee driving the protocol (NOT vs_lift's actor model).
  b) wasm + native support (vs_lift has none).
  c) The messaging approach (an EVOLUTION of braid for v0.6, per the Q-A/Q-C decisions above).
  d) W-parameter genericity in the cryptography (vs_lift lacks this).

REPLACE WITH VS_LIFT (the "brain"):
  a) The simplified protocol: simplified Configuration handling with NO Configuration signing round
     (config is a validity fact / implicit acceptance via signed Shares, per the aggregation
     decision), no Channels, symmetric computation of election public keys and plaintexts.
  b) The corresponding ascent datalog implementation.
  c) The stateright tests FOR THE MIXNET ONLY (v0.6 is about the mixnet, not other vs_lift parts).

CONSEQUENCES / SHARPENING:
  - Extraction boundary is precise: port vs_lift/trustee_application/ascent_logic/ (+ selected mixnet
    stateright tests). DISCARD top_level_actor.rs and handlers/ (the actor driver we do not take).
  - Datalog contract already fits: vs_lift's Message enum variants are hash-only contextual facts
    (CfgHash, SharesHash, ...) i.e. vs_lift Message ~= our Predicate (Q-A/Q-C). Our messaging
    evolution (c) is the adapter: WireMessage{head,body} -> verify -> Predicate ~= vs_lift Message
    -> datalog -> Action. (Strong consistency check that the two halves compose.)
  - W-genericity vs datalog: no collision. vs_lift rules are W-agnostic; W stays a Configuration
    field consumed by the action/crypto layer, not the datalog (matches cross-cutting decision).

DECISION: LocalBoard storage model — per-type collections, single predicate with a dual role
(supersedes the current two uniform HashMaps) — AGREED

Replaces today's design (two uniform maps: statements keyed by StatementEntryIdentifier +
artifacts_memory keyed by ArtifactEntryIdentifier, both carrying a hash-in-value for overwrite
detection, artifacts stored as serialized Vec<u8> and deser'd on every typed accessor).

SHAPE
- Split storage into PER-TYPE collections, one per message/artifact type (Shares, Mix, PublicKey,
  MixSignature, ...). Deserialized, type-safe values (no per-access deser, illegal states
  unrepresentable). Macro-generatable over the type list (reuse the dispatch macro that threads W).
- Each collection is HashMap<FullPredicate, Body> where:
    - KEY = the FULL predicate (the datalog relation tuple): sender + context/in-hashes +
      content/out-hash H(body) + type. Content-addressed: an action must name the exact hash it
      wants, and the store CANNOT return a body other than the one datalog authorized (a small
      safety GAIN vs slot-key + separate hash-check).
    - VALUE = just the deserialized body. The content hash is DROPPED from the value — it is already
      in the key (removes the redundant hash-in-value of the current design).
- The KEYSET *is* the datalog EDB. The map merely attaches bodies for actions to fetch. Loading
  storage -> ascent is a per-type copy; storage keys == relation tuples. One structure, dual role.

SINGLE PREDICATE, DUAL ROLE (the unification)
  1. Full predicate = content-addressed KEY (retrieval / "supply the exact hash") AND the datalog
     relation tuple.
  2. collides() = the SLOT PROJECTION of that same predicate (drops the content hash; keeps
     sender + type + position) = the write-once identity ("two different messages for the same slot
     are equivalent"). collides() is the ONLY definition of a "slot".

WRITE-ONCE LIVES ONLY IN DATALOG (the simplification)
- Storage no longer enforces write-once. It is a pure content-addressed set (+ bodies): identical
  messages dedupe by key; equivocating messages have DISTINCT full-predicate keys so BOTH are stored,
  become relations, and are caught by collides() over the SET -> HALT (order-independent).
- KEY REALIZATION: the current storage-layer "overwrite attempt" check was NEVER an independent
  guarantee — it is safe only because it also HALTs on a differing insert, i.e. it DUPLICATES
  collides(). (Had it silently kept the first, that would be first-wins = the Q5 fork we rejected.)
  So the projection-keyed storage-layer write-once is REDUNDANT for safety, not additive.

SAFETY ANALYSIS (Q: does datalog-only write-once reduce safety?)
- NO reduction of the core Q5 property (detect equivocation -> halt, order-independent), PROVIDED
  the invariant below holds. Anti-rewrite (§1d / Q-C) still holds: the persisted predicate set still
  pins H(body) (it is in the key). The storage check could not close any window collides() leaves
  open anyway (e.g. "acted on A in pass 1 before B arrived in pass 2" is identical either way).
- WHAT IS GIVEN UP: defense-in-depth against a MISSING or BUGGY collides() rule for some type.
- RECOVER IT BY CONSTRUCTION: GENERATE collides() from each predicate type's slot projection (same
  dispatch macro). Then collides() is TOTAL by definition — cannot forget a type — which recovers
  exactly the fail-safe the storage check gave, from the single source of truth. Strictly better than
  two hand-maintained copies (no divergence risk between a storage "slot" and a datalog "slot").

LOAD-BEARING INVARIANT (makes the simplification safe)
  Every storable message <-> exactly one predicate/relation that a TOTAL collides() ranges over, and
  inference ALWAYS evaluates collides() over the COMPLETE persisted set before any action is trusted
  (vs_lift's error(String) gating already does this).

CONSEQUENCES
- Q3/Q4 PARTLY DISSOLVES: the slot lives ONLY in datalog collides(), so position-vs-content-hash is
  a purely DATALOG-INTERNAL choice. Storage no longer mirrors the slot into a key; b4 (untrusted,
  Q-B) never enforced it — any b4 UNIQUE constraint is a pure AVAILABILITY optimization, not
  security. (This narrows item-8's "slot-key columns" coupling to a b4-availability detail.)
- FIXME (lost SQLite artifact storage) is resolved by Q-C, not reintroduced: persist PREDICATES
  (the keys); bodies stay transient/deserialized in memory and are re-fetched + self-certified
  (against the key's H(body)) on restart. The per-type in-memory collections and the predicate-only
  persistent layer are complementary, not redundant.
- Retrieval works because actions are DRIVEN by datalog: an action receives the full predicate(s) it
  acts on, so it always holds the exact key needed to fetch a body.

collides() EXECUTION MODEL — refined (answers "feel free to suggest another approach")

  storage-model decision eliminated). This collapses the user's "two variants" into ONE code path
  fed from two sources: persisted predicates at init + newly-arrived predicates during operation.

    - Re-execution is prevented for free: our OWN already-posted outputs are persisted predicates too,

RESOLUTION (closes the domain_tag micro-choice): signed_bytes = ser(Statement) — NO domain_tag

New detail made explicit: EVERY message's head context hashes include the CONFIGURATION MESSAGE HASH
(cfg_hash) as their first element. The Configuration message IS the domain — it defines the setting
(params, trustee + manager pubkeys). This is verified directly in the existing vs_lift datalog:
  - every relation leads with CfgHash:
      shares(CfgHash, TrusteeSharesHash, Sender), public_key(CfgHash, PublicKeyHash, Sender),
      mix(CfgHash, PublicKeyHash, in, out, Sender), mix_signature(CfgHash, ...),
      partial_decryptions(CfgHash, ...), configuration_valid(CfgHash, ...);
  - the prelude bootstraps configuration_valid from Message::ConfigurationValid(cfg_hash, ...) and

    (error("message cfg does not match context") <-- message(m1), configuration_valid(cfg_hash,...),
     if m1.get_cfg() != *cfg_hash;).

Consequence: a separate domain_tag is REDUNDANT and is DROPPED. cfg_hash already provides domain
separation, and because Configuration is PER-EXECUTION (Q17), it is a STRONGER separator than a
static tag: it separates not just "this protocol" but "this specific execution", so a signature from
execution A cannot be replayed into execution B (B's messages must carry B's cfg_hash, which won't
match A's signed statements). Final form:

    signed_bytes = ser(Statement)     (no domain_tag, no type_tag)

Bootstrap edge case: the Configuration message is the root and cannot reference its own hash. Its
authenticity is anchored OUT-OF-BAND at bootstrap (Q8), not by a domain tag; its hash then becomes
the domain for every subsequent message. The type discriminant in ser(Statement) still distinguishes
a Configuration statement from all other types. Spec §3.3 updated accordingly.

RESOLUTION (relaxes Q-C's H(body) type domain-separation): NOT needed — H(body) is never standalone

Q-C wrote "To prevent cross-type body confusion under a bare-hash fetch, H(body) is domain-separated
by type (hashing the type alongside the body)". Under the adopted storage model this guard is
UNNECESSARY (it may still be done, but buys nothing): H(body) is NEVER used as a bare/standalone hash.
