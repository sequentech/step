Tasks for braid 0.6

* messages, slots and b4
    * Messages retain a single structure at the wire level, something like
        - sender
        - signature
        - type: enum indicates what specific struct is in the payload
        - payload, serialization of a specific struct
            - header
                - date
                - other common header fields
                - fields for hashes that set the context for that struct
            - specific fields for that struct

        The only serialization operation to verify the message is deserializing the payload, which is what the signature is over. There is no need to reserialize things in order to verify signatures.
    
    * b4 and message ordering 
    
    In the current implementation trustees maintain a local message order to ensure that the remote board
    cannot rewrite history by exploting gaps in message order. The trustee maintains this local order
    to decide which message takes precedence when slots collide. Instead, we should a)
    handle this at a unified board client, and b) apply the rule that once a slot is filled it is fixed, dropping trustee's tracking of local order altogether. 
    
    Message order, as sequenced by b4, only affects how the client's slots are filled, but there is no explicit ordering of messages at the board client or trustee, and no corresponding precedence logic at all (except the logic that a slot once filled is fixed). This requires that the message persistence functionality (see below points) is aware of slots and is enforcing them. (note that b4 should not include an order field in its messages either, it could have an internal order for its own purposes, but does not need to make this explicit in the messages data it responds with: the _only_ case in which b4 would care about the order it sends its messages in is if it's behaving maliciously; order differences _could only_ have observable effects if slot collisions exist, and board clients are not enforcing write-once slots)

    * Message slots
        - instead of the ad-hoc StatementEntryIdentifier and ArtifactEntryIdentifier there is a single
        slot field/computation for each message that implements the collision logic necessary for append
        only semantics. The slot computation should be composed of _at least_
            - the sender (the 0-based index of the trustee in the configuration list)
            - the type of message (as in the wire message structure)
            - for mix signatures, the position of the mix (that is being signed) in the mix chain, or 0 if it is not a mix signature. It is also possible to put this in the message type, and have variants within
            the mix signature type for each position, since the number of trustees will be capped anyway, eg

            enum Type {
                Configuration,
                ConfiguratioNSignature,
                PublicKey,
                ...
                MixSignature(MixPosition)
            }

            and

            enum MixPosition {
                One = 1,
                Two = 2,
                ...
            } (see also https://doc.rust-lang.org/std/mem/fn.discriminant.html#accessing-the-numeric-value-of-the-discriminant)

        it is a security requirement that slots distinguish messages unequivocally, and the above should be the minimum amount of information necessary for this. Because slot input data is constrained by the protocol parameters, it could be a good idea to compute slots from the Configuration struct: for example, asking
        for the slot for the 5th mix signature should fail if the Configuration has 2 trustees (or a threshold less than 5)

        - The board client then stores messages in memory keyed by this slot, for example using a hashmap like 'HashMap<Slot, MessageEntry>' where MessageEntry contains the hash of the message being retrieved to sanity check it is the correct data as specified by some datalog predicate. The current logic, whereby a message is only accepted into memory (and queryable by the trustee) once the corresponding persistent data has been saved is retained, this is a crucial
        requirement to prevent tampering by the remote board. The message update cycle is as before: messages retrieved by board client => digests persisted => stored in memory => used by trustee which then posts
        action result messages => posted remotely by the board client => retrieved by board client... In particular,
        a message produced by a trustee takes no effect locally until it comes back from the remote board, as in the current implementation.

    * Unify the local board and remote board
        * This new unified board is responsible for 1) Interacting with the remote board, posting and retrieving, 2) Storing messages in memory for access by the trustee, 3) Handling digest persistence in a unified way, using
        only digests (as in the current wasm implementation of the local board) and not full messages (as in the current native implementation). For reference, the current implementation has both 'local_board' and 'http' boards that correspond to the local and remote board in this description. We will have to verify whether the changes described above that aim to simplify messages are compatible with this unification, in particular, whether they are compatible with the two step process that http boards use to transfer large amounts of data through s3.

* Bootstrapping and the configuration message

    Because the configuration message is necesary to do anything at all, relevant protocol structs should
    require it on construction. For example, the SessionTrustee struct (previously named just 'Trustee') should
    require a configuration message to be constructed, a SessionTrustee  is not updated with this message, it is built with it, and stores it in a custom field. In other words, the configuration message is not part of the protocol execution, but of protocol initialization.

    This could also be relevant for the board client, because it needs a configuration message to verify signatures
    for every message it retrieves. In fact, the configuration message could be part of the 'boards' table in b4
    rather than the 'messages' table.

* The 'batch' protocol field

    In the current implementation, messages after the dkg, that is, for shuffling and decryption, have an extra
    batch field that acts as a namespace. Rather than have this field explicitly in messages and in datalog predicates, it would be simpler to make the protocol unaware of batches altoghether, and have b4 and the board
    client support this functionality. One way to do this is if boards have a (single) parent child relationship, such that child boards inherit all messages from their parent board. For example, the board 'dkg_board' could have a child 'dkg_board/tally_1' such that requesting messages for board 'dkg_board/tally_1' also returns messages from dkg_board. 

* New protocol datalog implementation

    Datalog inference is now 1) implemented with the more modern ascent crate, and 2) Uses the datalog implementation (rules) from the votesecure project, modifying it where necessary. Those rules have a higher assurance level and also do not have 'batch' fields which fits in with the previous point regarding the 'batch' protocol field being dropped. Please refer to the 'vs_lift' directory and its 'trustee_application/ascent_logic' directory where the newer votesecure datalog implementation (and the rest of the trustee implementation) has been lifted.
    Note, we do not wish to integrate or recreate the complete votesecure mixnet implementation, we only want to use its updated datalog logic, with whatever (hopefully) minor changes are required to be integrated into braid.

* Per-protocol execution signing keys and symmetric key removal

    * Signing keys
    
        In current deployments trustee signing keys are fixed (shared) across protocol executions. In the next version this requirement will be relaxed. Because a SessionTrustee is _supplied_ a signing keypair on construction, the SessionTrustee is not involved in this keypair generation nor is it part of the protocol. This is handled by whoever calls the SessionTrustee on construction, which can decide instead to use
        per-execution signing keys, provided this caller guarantees that for a given protocol execution, the same keypair is supplied (in the event that for example the trustee must restart at a later time and its memory is wiped)

    * Symmetric encryption of per-execution public keypairs for share encryption

        In the current implementation, a fixed symmetric cipher is used to encrypt a trustee's per-execution
        share-encryption keypair. This encrypted keypair, together with its public key, are posted in the Channel
        message as part of protocol execution. In the new version generation of share encrypting keypairs is no longer part of the protocol (as is already the case for signing keypairs). A SessionTrustee must be provided with its share encrypting keypair by its caller. Additionally, because the Channel message no longer exists, trustees must also be provided with the public key that corresponds to its peers' share encryption keypair, such that shares can be decrypted by their recipient. Again, the caller must guarantee that for a given protocol execution, the same keypair is supplied (in the event that for example the trustee must restart at a later time and its memory is wiped)

    Im summary, 1) generation and handling of signing keypairs is now optionally per-execution; because the SessionTrustee is provided this information on construction, the caller can decide to use per-execution signing keypairs, 2) generation and handling of share encrypting keypairs is moved out of the protocol and out of a SessionTrustee, symmetric encryption is removed outright, and share encrypting public keys are added to the configuration message (as is already the case for signing public keys)
    
    In a wasm setting, the browser will be responsible for generating secret material locally, and its reconstruction at a later date depends on the browser user having stored this information for later executions (where the browser's memory will be empty). In a server setting, deployments can continue to use a single configuration file (which contains the signing and share encrypting keypairs) for all protocol executions, or instead use per-execution keys. The SessionTrustee does not know ore care which deployment is chosen, it simply receives this information externally.
