The voting portal uses the vendored Apache-2.0 `@vitrine/verify` package for every check. It uses `@vitrine/ui` only for the `<vitrine-status>` element of the booth refusal dialog. The ballot status, its dialog and the ballot tracker's receipt are the portal's own components, and their wording is in the portal's translations (`vitrine.status`, `vitrine.record`, `ballotLocator.search`, `ballotLocator.audit` and `ballotLocator.result`), not in the packages. Step communicates with its sidecar through Harvest and does not depend on Vitrine Rust crates.

Before encryption, `vitrine_voter_context` supplies witnessed config and voting-opened receipts. Public policies are pinned from `presentation.vitrine`; private policies come from the authenticated context and must match the presentation's pinned ID. The SDK's new-pin admission checks profile meanings and infrastructure minimums, then its booth check binds the key, exact ballot style, served style-digest list, election, event, policy and the portal's own build release. A refusal stops encryption and schedules a bounded observation for the pinned policy's monitors. Observations contain configuration receipts and public configuration inputs, never a voter's encrypted ballot or submission receipt.

After either cast path, the confirmation slice carries the typed Vitrine answer. Receipt processing cannot turn an accepted cast into a failed cast. All four answers (`receipt`, `promise`, `queued`, `unavailable`) are handled as data. At-cast position requests go only to the log. Private events use `vitrine_voter_forward`: `upgrade` and `opening` carry the voter's receipt or promise, while `policies` has an empty string body and returns `vitrine/policy-proofs/v1`. Harvest authenticates the event's voter; only ballot-specific routes require proof of ownership of that ballot. The client verifies policy proofs before updating its accepted policy history. Failed or missing discovery leaves claims pending.

The voter sees a ballot's ID as its Tracking ID. The API, the database and the code keep the name ballot ID (`ballot_id`, `ballotId`). Tracking IDs are formatted by `services/vitrine/ballotId.ts`: lowercase hexadecimal in groups of four, with the short ID being the first two groups (8 of the 64 characters). It also classifies what a voter types or pastes as empty, short, full or invalid, and groups it as it is typed. `services/vitrine/ballotStatus.ts` turns a receipt's check (`IReceiptView`) into an `EBallotStatus`: `notcast`, `checking`, `recorded`, `witnessed`, `verified`, `late` or `problem`. The enum also has `auditable` and `auditfail` for an audited ballot, which is never cast. `ballotTagOf` gives the tag that goes next to the ID, an `EBallotTag`: `notCast`, `cast` or `auditable`. The worst step wins: a problem over a late step over one still on its way. A `problem` has a cause, `EBallotProblem`: `mismatch` (validly signed objects contradict each other, which is evidence), `damaged`, `no-receipt` (the event requires a receipt and there is none) or `unchecked`. The same file maps the check's tiers to the dialog's three steps: `record`, `witnesses`, and `hubs` with `browser` as the anchors. `services/vitrine/statusRows.ts` builds the dialog's headline, steps and caption as translation keys with values, so that the wording stays in the translations and what each text claims stays next to the data it rests on.

`components/Vitrine/BallotStatusIcon.tsx` draws the check mark: one or two checks, a solid, dotted or dashed line, grey, blue, amber or red, and a clock or alert badge. `StatusTag.tsx` draws the pill of a tag, with a tone (`EStatusTone`: neutral, success, info, warning or danger), and `BallotTag.tsx` gives it the words of an `EBallotTag`. A copy button swaps its icon for a green check for a moment: `useCopyFeedback`, in `hooks/useCopyFeedback.ts`, does it for the tracker's full ID and for the record viewer, the ID boxes use `BallotHashCopyButton` of `ui-essentials`, which takes the colour of the check as `copiedColor`, and the dialog keeps its own. `BallotStatus.tsx` renders the check mark as a 34 px button next to a Tracking ID (`BallotStatusButton`) or as the **Ballot cast** label of the ballot list (`BallotCastButton`), and opens `BallotStatusDialog.tsx`: the Tracking ID with its tag, the short and full ID with a copy button, the headline, the three steps, the explanations of a late or failed check, and the **Save receipt**, **Save evidence** and **Open in the ballot tracker** actions. Saving writes the receipt chain to a `.vitrine-receipt` file named by `receiptFileName`, and makes no request. The dialog also draws `auditable` and `auditfail`, but no screen gives it those two statuses today: the tracker shows an audited ballot through `TrackerAudit.tsx`. The review screen uses the status through `ReviewBallotId.tsx`, always as `notcast`. `ReviewScreen.tsx` lays the steps, the title and that box out in its `ReviewHeader` grid: the box sits next to the title on a wide screen, under it at 900 px or less, and above the steps on a phone. In the box the short ID is a button that opens the full ID. The confirmation screen gets the receipt of the ballot just cast from `useCastReceipt`, which keeps it on the device unless the session is a kiosk. The ballot list gets the receipts that this browser kept from `useKeptReceipts`, and gives the status to `SelectElection` in `ui-essentials` as its `votedStatus`; an election without a kept receipt keeps the **Voted** label. When an event keeps a transparency log and the voter cast every ballot an open election allows, `showsAlreadyCastHint` in `services/vitrine/ballotList.ts` is true and `SelectElection` gets `alreadyCast`: the vote button is off, with "You already cast this ballot" as its tooltip and as a description for screen readers. Events without transparency keep Step's own Tracking ID box.

The ballot tracker, named Ballot Tracking on screen, is `routes/BallotLocator.tsx` and `components/BallotLocator/`. It finds a ballot by its short or full Tracking ID, with or without spaces. `ballotLookupOf` in `services/vitrine/ballotTracker.ts` looks a short ID up as a prefix (`ballotIdPrefix`): 8 characters, or 4 when telephone voting is enabled for the election. Several matches are listed with their full IDs and cast times (`BallotMatches`) for the voter to choose from. When the event's transparency is on, `TrackerSearch` draws the search, with its field, format chips and three cards, and `TrackerResult` shows the full receipt: `useTrackedReceipt` takes the receipt this device keeps or, for public events, asks the log once, with the ballot's cast time. Its four steps come from `trackerSteps` in `ballotTracker.ts`, which leaves out the tiers that the policy does not use. The ballot's record is shown by `components/Vitrine/RecordViewer.tsx`: a card with a one-line preview that expands into the text laid out with line numbers, and buttons that copy it and save it as a file; `services/vitrine/record.ts` reads its format, its size and the colours of a line of JSON. `classifyRecord` in `ballotTracker.ts` tells a cast ballot's record from an audited ballot's, which carries its ballot style and the plaintext and randomness of its ciphertext. For an audited ballot, `auditBallot` in `services/vitrine/ballotAudit.ts` runs the checks of the standalone ballot verifier: the ballot's hash is the Tracking ID, its ciphertext reproduces from the plaintext and randomness it carries, and only then does it decode into the voter's selections. Its `EAuditOutcome` is `verified`, `mismatch` or `not-verifiable`, when the checks could not run. `components/BallotLocator/TrackerAudit.tsx` shows the selections as **Your selections, decoded** for the first, an **Audit failed** card for the second and, for the third, a card titled **The audit could not be checked**. Step does not publish audited ballots, so the tracker shows this view only for a record that holds one. **Check it independently** calls `openVerifier` in `services/vitrine/handoff.ts`, which opens the ballot verifier's receipt screen in a new tab with the chain in the link's fragment, which browsers never send to a server. Without transparency, the classic locator keeps `BallotIdField`, the matches as rows and the content in a plain box.

The ballot verifier has its own `services/vitrine/ballotId.ts` and `ballotStatus.ts`, which give the short ID and the three steps the same meaning, and its own `BallotStatusIcon.tsx`. Step 2 of the audit uses `BallotIdField`, which groups the digits as they are typed and accepts only a full Tracking ID: a short ID has 32 bits, which a birthday search could match. `GroupedBallotId` shows the decoded ID and the one provided in groups, and highlights the groups that differ. The receipt screen renders its result with `ReceiptStatus.tsx`, the status and its three steps, and no longer uses the kit's `<vitrine-receipt>` and `<vitrine-proof-steps>` elements. It loads `@vitrine/ui` only for the words of a trust policy.

The one React wrapper left for a kit element, `VitrineStatusView` in `components/Vitrine/VitrineElements.tsx`, sets the element's message through a ref after the custom elements are defined. Portal `cat` maps to kit `ca`. Device storage is partitioned by election and bound to the authenticated account; kiosk mode and the storage layer's opt-out keep no receipt, and no screen sets that opt-out now. The pre-encryption preview path is explicitly separate from an authenticated cast.

The admin **Transparency** tab appears after **Logs** and requires `election-event-transparency-tab`. All three GraphQL operations use that role. The tab shows public-mode refusal, a Board draft with eight computed words, sealed policies with six computed words and IDs, service status, witness lag, hub anchors, enrolment notes and a validated explorer link. It treats server strings and uploaded files as data.

Refresh browser packages without modifying the Vitrine checkout:

```sh
scripts/vendor-vitrine.sh /path/to/vitrine main
cd packages
yarn install --ignore-scripts
```

The script exports an immutable commit with `git archive`, installs its locked dependencies, builds and tests both packages, and packs the resulting tarballs. Commit the tarballs, `VITRINE_COMMIT`, `SHA256SUMS` and `packages/yarn.lock` together. Failed upstream checks stop vendoring. The frontend GraphQL action types are kept alongside the operations until the merged backend schema is regenerated by the integration coordinator.
