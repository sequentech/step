The voting portal uses the vendored Apache-2.0 `@vitrine/verify` package for every check. It uses `@vitrine/ui` only for the `<vitrine-status>` element of the booth refusal dialog. The ballot status, its dialog and the ballot tracker's receipt are the portal's own components, and their wording is in the portal's translations (`vitrine.status`, `vitrine.record`, `ballotLocator.search`, `ballotLocator.audit`, `ballotLocator.result`, `auditScreen.check` and `reviewScreen.auditConfirm`), not in the packages. Step communicates with its sidecar through Harvest and does not depend on Vitrine Rust crates.

Before encryption, `vitrine_voter_context` supplies witnessed config and voting-opened receipts. Public policies are pinned from `presentation.vitrine`; private policies come from the authenticated context and must match the presentation's pinned ID. The SDK's new-pin admission checks profile meanings and infrastructure minimums, then its booth check binds the key, exact ballot style, served style-digest list, election, event, policy and the portal's own build release. A refusal stops encryption and schedules a bounded observation for the pinned policy's monitors. Observations contain configuration receipts and public configuration inputs, never a voter's encrypted ballot or submission receipt.

After either cast path, the confirmation slice carries the typed Vitrine answer. Receipt processing cannot turn an accepted cast into a failed cast. All four answers (`receipt`, `promise`, `queued`, `unavailable`) are handled as data. At-cast position requests go only to the log. Private events use `vitrine_voter_forward`: `upgrade` and `opening` carry the voter's receipt or promise, while `policies` has an empty string body and returns `vitrine/policy-proofs/v1`. Harvest authenticates the event's voter; only ballot-specific routes require proof of ownership of that ballot. The client verifies policy proofs before updating its accepted policy history. Failed or missing discovery leaves claims pending.

The voter sees a ballot's ID as its Tracking ID. The API, the database and the code keep the name ballot ID (`ballot_id`, `ballotId`). Tracking IDs are formatted by `services/vitrine/ballotId.ts`: lowercase hexadecimal in groups of four, with the short ID being the first two groups (8 of the 64 characters). It also classifies what a voter types or pastes as empty, short, full or invalid, and groups it as it is typed. `services/vitrine/ballotStatus.ts` turns a receipt's check (`IReceiptView`) into an `EBallotStatus`: `notcast`, `checking`, `recorded`, `witnessed`, `verified`, `late` or `problem`. The enum also has `auditable` and `auditfail` for an audited ballot, which is never cast. `ballotTagOf` gives the tag that goes next to the ID, an `EBallotTag`: `notCast`, `cast` or `audited`. The worst step wins: a problem over a late step over one still on its way. A `problem` has a cause, `EBallotProblem`: `mismatch` (validly signed objects contradict each other, which is evidence), `damaged`, `no-receipt` (the event requires a receipt and there is none) or `unchecked`. The same file maps the check's tiers to the dialog's three steps: `record`, `witnesses`, and `hubs` with `browser` as the anchors. `services/vitrine/statusRows.ts` builds the dialog's headline, steps and caption as translation keys with values, so that the wording stays in the translations and what each text claims stays next to the data it rests on.

`components/Vitrine/BallotStatusIcon.tsx` draws the check mark: one or two checks, a solid, dotted or dashed line, grey, blue, amber or red, and a clock or alert badge. `StatusTag.tsx` draws the pill of a tag, with a tone (`EStatusTone`: neutral, success, info, warning or danger), and `BallotTag.tsx` gives it the words of an `EBallotTag`. A copy button swaps its icon for a green check for a moment: `useCopyFeedback`, in `hooks/useCopyFeedback.ts`, does it for the tracker's full ID and for the record viewer, the ID boxes use `BallotHashCopyButton` of `ui-essentials`, which takes the colour of the check as `copiedColor`, and the dialog keeps its own. `BallotStatus.tsx` renders the check mark as a 34 px button next to a Tracking ID (`BallotStatusButton`), and opens `BallotStatusDialog.tsx`: the Tracking ID with its tag, the short and full ID with a copy button, the headline, the three steps, the explanations of a late or failed check, and the **Save receipt**, **Save evidence** and **Open in the ballot tracker** actions. Saving writes the receipt chain to a `.vitrine-receipt` file named by `receiptFileName`, and makes no request. The dialog also draws `auditable` and `auditfail`, with the tag `audited`. The review screen uses the status through `ReviewBallotId.tsx`, as `notcast`; the audit screen uses the same box in its `audited` state, which opens the dialog as `auditable`. The tracker shows an audited ballot through `TrackerAudit.tsx`. `ReviewScreen.tsx` lays the steps, the title and that box out in its `ReviewHeader` grid: the box sits next to the title on a wide screen, under it at 900 px or less, and above the steps on a phone. In the box the short ID is a button that opens the full ID. The confirmation screen gets the receipt of the ballot just cast from `useCastReceipt`, which checks and upgrades it in the page's memory only. The portal keeps no receipts and no Tracking IDs in the browser, so later checks start from the receipt the voter saved, and the ballot list keeps the **Voted** label of `SelectElection` in `ui-essentials`, with no check mark. On start, `forgetDeviceReceipts` in `services/vitrine/deviceReceipts.ts` removes what earlier versions left: the `vitrine-receipt:` keys and the keep-or-forget choice in localStorage, and the `vitrine-receipts` IndexedDB database of Vitrine's receipt store. It writes nothing. Only the tab-scoped markers of a ballot being cast (`sentBallotMarker.ts`, `sessionBallotData.ts`) stay in sessionStorage, and they end with the tab. When an event keeps a transparency log and the voter cast every ballot an open election allows, `showsAlreadyCastHint` in `services/vitrine/ballotList.ts` is true and `SelectElection` gets `alreadyCast`: the vote button is off, with "You already cast this ballot" as its tooltip and as a description for screen readers. Events without transparency keep Step's own Tracking ID box.

The confirmation screen, `routes/ConfirmationScreen.tsx`, is drawn by `ConfirmationLayout` and `ConfirmationActions` of `ui-essentials` (design v42) for every event. On a wide screen the outcome (the title, the election and the cast time, `view.own.acceptedAt` formatted as in the status dialog) and **Keep your receipt** are on the left, and the receipt is a ticket on the right, `aside.confirmation-ticket`; on a phone it is one column in DOM order: outcome, ticket, **Keep your receipt**, updates. The ticket shows the Tracking ID with its help button and, below a perforation, the QR code. With transparency the portal passes the short ID with the status check, the **Cast** tag and `FullTrackingId` in its `ticket` surface; without it, the whole ID with the copy button. **Save receipt (PDF)** (`save-receipt-button`, which keeps `print-receipt-button`) downloads the receipt PDF as **Print** did, and **Finish** ends the row. The row has no line about the cast email: whether `BALLOT_RECEIPT` is emailed is decided by the report configuration on the server, which the portal does not load, so `ConfirmationActions` takes `castEmailSent` and the portal leaves it off. The screen has no help icon of its own; the Tracking ID keeps its help. `components/Vitrine/GetUpdates.tsx` draws the optional **Get email updates** under a rule, after the actions, with no box: equal tiles of the hubs, each with its name and who runs it, in the order `shuffled` draws once for each visit. It is left out when `hub_updates.confirmation` is `off`, when the policy has no hub with a site, and in the kiosk. An acclaimed election shows no ticket, and a blank ballot says so under the title.

The ballot tracker, named Ballot Tracking on screen, is `routes/BallotLocator.tsx` and `components/BallotLocator/`. It finds a ballot by its short or full Tracking ID, with or without spaces. `ballotLookupOf` in `services/vitrine/ballotTracker.ts` looks a short ID up as a prefix (`ballotIdPrefix`): 8 characters, or 4 when telephone voting is enabled for the election. For a public event, `useShortIdMatches` first asks the policy's log server and monitors for the short ID's bucket (`lookupShortId` in `services/vitrine/shortId.ts`, over `lookupTrackingId` of `@vitrine/verify`), so that no server learns which ballot was looked for; the `LOCATE_BALLOT` route, which sends the typed ID, answers only when no server has the bucket route (and the page then says that the server sees the exact ID), for a private event, or for a voter who holds no policy. Up to five ballots are listed with their full IDs and the third group highlighted (`ShortIdMatches`), and none is marked as the voter's: only the full Tracking ID on the receipt says which is theirs. Above five, the page asks for the third group. The Logs tab searches the same way. When the event's transparency is on, `TrackerSearch` draws the search, with its field, format chips and three cards, and `TrackerResult` shows the full receipt: `useTrackedReceipt`, for public events, asks the log once for the receipt, with the ballot's cast time; otherwise the page points to the receipt file the voter kept. Its four steps come from `trackerSteps` in `ballotTracker.ts`, which leaves out the tiers that the policy does not use. The ballot's record is shown by `components/Vitrine/RecordViewer.tsx`: a card with a one-line preview that expands into the text laid out with line numbers, and buttons that copy it and save it as a file; `services/vitrine/record.ts` reads its format, its size and the colours of a line of JSON. `classifyRecord` in `ballotTracker.ts` tells a cast ballot's record from an audited ballot's, which carries its ballot style and the plaintext and randomness of its ciphertext. For an audited ballot, `auditBallot` in `services/vitrine/ballotAudit.ts` runs the checks of the standalone ballot verifier: the ballot's hash is the Tracking ID, its ciphertext reproduces from the plaintext and randomness it carries, and only then does it decode into the voter's selections. Its `EAuditOutcome` is `verified`, `mismatch` or `not-verifiable`, when the checks could not run. `components/BallotLocator/TrackerAudit.tsx` shows the selections as **Your selections, decoded** for the first, an **Audit failed** card for the second and, for the third, a card titled **The audit could not be checked**. The tracker shows this view for a record that holds an audited ballot with its published secret. **Check it independently** calls `openVerifier` in `services/vitrine/handoff.ts`, which opens the ballot verifier's receipt screen in a new tab with the chain in the link's fragment, which browsers never send to a server. Without transparency, the classic locator keeps `BallotIdField`, the matches as rows and the content in a plain box.

The audit is `routes/AuditScreen.tsx`. Both the review screen's audit button and the status dialog's **Audit ballot** open the confirmation. For an event that keeps a transparency log it is `components/Vitrine/AuditConfirmDialog.tsx`, which says what happens, with **Cancel** and **Audit ballot**, stacked on a phone; otherwise the classic warning. Once the ballot box acknowledges the audit, an event that keeps a log gets `components/Vitrine/AuditCheck.tsx`: the review screen's `ReviewBallotId` box in its `audited` state, three steps (encrypted on this device, opened in the public record, compare it on a hub), **Why audit?** collapsed, and **Vote again**. The third step lists `auditHubs` from `services/vitrine/hubUpdates.ts`, the policy's hubs with a `hub-ballot-verifier` line, as equal tiles that `shuffled` orders at random each time the screen appears. Each tile links to `auditedBallotLink`: `<ballot verifier>tenant/<t>/event/<e>/election/<el>/audited#id=<full Tracking ID>&policy=sha256:<hex>`, with both values in the fragment. With no such hub, the screen offers the deployment's `BALLOT_VERIFIER_URL` as the election's ballot verifier, and without that, the ballot in the tracker. The screen has no download, no ballot JSON, no verifier steps and no Print. An event without a log keeps the classic screen, where the download is the only way to audit.

The ballot verifier has its own `services/vitrine/ballotId.ts` and `ballotStatus.ts`, which give the short ID and the three steps the same meaning, and its own `BallotStatusIcon.tsx`. Step 2 of the audit uses `BallotIdField`, which groups the digits as they are typed and accepts only a full Tracking ID: a short ID has 32 bits, which a birthday search could match. `GroupedBallotId` shows the decoded ID and the one provided in groups, and highlights the groups that differ. The upload flow stays for events without a log. For a hub, the verifier also has the audited ballot screen, `screens/AuditedScreen.tsx` at `/tenant/:tenantId/event/:eventId/election/:electionId/audited`, which opens the ballot of the link's fragment from the public record with no login and no upload (`services/vitrine/auditedBallot.ts`, `screens/hooks/useAuditedBallot.ts`), and asks the voter to compare the decoded choices. `HUB_NAME` and `VOTING_PORTAL_URL` in its settings name the hub in the page's header and the voting site for **Back to the voting site**. See [A hub's ballot verifier](../14-vitrine.md#a-hubs-ballot-verifier). The receipt screen renders its result with `ReceiptStatus.tsx`, the status and its three steps, and no longer uses the kit's `<vitrine-receipt>` and `<vitrine-proof-steps>` elements. It loads `@vitrine/ui` only for the words of a trust policy.

The one React wrapper left for a kit element, `VitrineStatusView` in `components/Vitrine/VitrineElements.tsx`, sets the element's message through a ref after the custom elements are defined. Portal `cat` maps to kit `ca`. The pre-encryption preview path is explicitly separate from an authenticated cast.

The admin **Transparency** tab appears after **Logs** and requires `election-event-transparency-tab`. All three GraphQL operations use that role. The **Election authority contact** section (`AuthorityContact.tsx`, `services/AuthorityContact.ts`) and the hub problems notice (`HubProblems.tsx`, `services/HubProblems.ts`) are described in the Vitrine developer guide. The tab shows public-mode refusal, a Board draft with eight computed words, sealed policies with six computed words and IDs, service status, witness lag, hub anchors, enrolment notes and a validated explorer link. It treats server strings and uploaded files as data.

Refresh browser packages without modifying the Vitrine checkout:

```sh
scripts/vendor-vitrine.sh /path/to/vitrine main
cd packages
yarn install --ignore-scripts
```

The script exports an immutable commit with `git archive`, installs its locked dependencies, builds and tests both packages, and packs the resulting tarballs. Commit the tarballs, `VITRINE_COMMIT`, `SHA256SUMS` and `packages/yarn.lock` together. Failed upstream checks stop vendoring. The frontend GraphQL action types are kept alongside the operations until the merged backend schema is regenerated by the integration coordinator.
